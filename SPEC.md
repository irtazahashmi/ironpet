# ironpet v1 spec

A personal macOS desktop pet that floats above all windows, watches coding agents, and runs agent tasks for me.

## Decisions

| Area | Decision |
| --- | --- |
| Audience | Just me. Rough edges are fine. |
| Platform | macOS only, native Swift (AppKit + SwiftUI), Dock app. |
| v1 jobs | Agent watcher, quick chat, screen-aware help. |
| Later | Focus coach, calendar, dev signals, more chat backends, auto-hide. |
| Movement | Stays where dragged (position persists). Idle animations, eyes follow cursor. |
| Art | Ghost, a chibi white direwolf in a Night's Watch cloak, drawn in code by `tools/make_pet.swift` (alternates: Mochi, a mint wolf, and a hamster, panda, bunny and cat on the same body and poses) into the Codex v2 atlas layout (1536x2288, 8x11 cells of 192x208). |
| Success | I stop alt-tabbing to check agents, fire small tasks from the pet, use screenshot help daily. |

## Agent watcher

- Watches Cursor (IDE chats and CLI) and Claude Code via global hooks that the pet installs itself.
  - Merges into each watched agent's own config, preserving other entries (Superset, Orca): `~/.cursor/hooks.json`, `~/.claude/settings.json`, `~/.codex/hooks.json`, `~/.gemini/settings.json`. GitHub Copilot gets its own file in `~/.copilot/hooks/` and Pi gets an extension in `~/.pi/agent/extensions/` that calls the same hook script. `SessionStore` maps each agent's events (Codex uses Claude's names; Gemini's are BeforeAgent/AfterAgent/BeforeTool; Copilot's are camelCase; Pi's come from the extension). The agents offered are the ones found on this Mac.
  - Backs up each file once to `<file>.ironpet-backup` before the first write. Uninstall removes only ironpet entries.
- Hooks POST to the pet on `127.0.0.1` with a token from `~/.ironpet/token`. The hook never blocks or fails the agent (1s timeout, always exits 0).
- Status per session: `running`, `needsInput`, `done`, `failed`, `idle`.
- Pet shows one mood by priority `needsInput > failed > done > running` with a count badge. Click opens the session list.
- `done` and `failed` stay until acknowledged (clicked, jumped to, or a new prompt starts).
- Speech bubble (and optionally a macOS notification) on entering `needsInput`, `failed`, `done`.
- Jump to source: iTerm tab when the hook saw `ITERM_SESSION_ID`, otherwise the Cursor window for the workspace (`open -a Cursor <root>`). Exact Cursor chat/terminal tab is out of scope.
- Open in the app that ran the session, on the exact tab or thread when the hook saw an id. The hook forwards only `CMUX_WORKSPACE_ID`, `CMUX_SURFACE_ID`, `T3CODE_THREAD_ID`, `HC_TERMINAL_ID` and `ORCA_TERMINAL_HANDLE` (never the whole environment); `SessionStore` keeps them on the session origin, in memory like the rest of the session. The session row, the done and needs-input bubbles and notifications all call `SourceJumper.jump`, which resolves the app with `Editors.resolve`. Built-in openers:
  - cmux (`com.cmuxterm.app`): `cmux://workspace/{cmux_workspace}/surface/{cmux_surface}`. Needs cmux 0.64.18 or later.
  - T3 Code (`com.t3tools.t3code`): `t3code://threads/{t3_env}/{t3_thread}`, where `t3_env` is read from `~/.t3/userdata/environment-id`.
  - Orca (`com.stablyai.orca`): runs `orca worktree activate --worktree path:<folder>` and activates the app, then `orca terminal switch --terminal <handle>` when the hook captured `ORCA_TERMINAL_HANDLE`. The folder is the nearest parent holding `.git`, because Orca matches `path:` exactly, and is passed as one argument. A folder that is no worktree, a failing command or a missing `orca` only logs once and still activates the app.
  - herdr (`dev.herdr.app`): runs `herdr-app do agent.focus --terminal <id>` as an argument list without a shell, then activates the app. The program is a bare name looked up on `PATH`, in the usual install folders and in the app bundle. The headless `dev.herdr.core` owner counts as `dev.herdr.app`.
  - Claude desktop (`com.anthropic.claudefordesktop`): `claude://code/needs-input?session={session}` for Claude Code sessions.
  - Codex (`com.openai.codex`, inside ChatGPT.app): `codex://threads/{session}` for Codex sessions.
  Session values are percent-encoded. A template with a placeholder the session cannot fill, or a scheme no app handles, only activates the app. The cmux, T3 Code, Claude and Codex link formats come from the apps' source and bundles, not documentation. Whether Claude's `session=` takes the hook's session id and whether a Codex thread id equals its session id is unverified. A session that already ended opens from the activity log, which keeps only the app, workspace and iTerm tab, so those openers only activate the app.

### Event mapping

| Source | Event | Effect |
| --- | --- | --- |
| Cursor | `sessionStart`, `beforeSubmitPrompt`, `postToolUse`, `afterAgentResponse` | running (headless CLI never fires `beforeSubmitPrompt`) |
| Cursor | `stop` (`status`: completed / error / aborted) | done / failed / idle |
| Cursor | `sessionEnd` | remove unless unacknowledged done/failed |
| Claude Code | `UserPromptSubmit`, `PreToolUse`, `PostToolUse` | running |
| Claude Code | `Notification` (`permission_prompt`) | needsInput |
| Claude Code | `Stop` | done |
| Claude Code | `SessionEnd` | remove unless unacknowledged done/failed |

Cursor also runs Claude Code hooks from `~/.claude/settings.json` ("Third-Party Imports", on by default, always on in cursor-agent), so each Cursor event would arrive twice, the second time labelled Claude Code and often without a folder. The hook script exits early for `claude` when `CURSOR_VERSION` is set (only Cursor sets it for hooks), and the app drops `claude` events whose payload has `cursor_version`.

Known gap: Cursor has no hook for "waiting on the user's approval", so Cursor sessions never show `needsInput`.

## Quick chat (milestone 2)

- ⌥⌘G (or clicking the pet when no watched agent needs attention) opens the ironpet window on Chat, with the input focused. Opening it activates ironpet (and closing it reactivates the previous app), because Wispr Flow (hold fn) finds the focused text field through the frontmost app's Accessibility tree. A dictation shows up as one large insert; with "Send automatically after dictation" on, it sends after 0.8s.
- When the chat opens from another app and Accessibility is already trusted, ironpet reads that app's focused `AXSelectedText` once (never in the background, never from a secure field, ironpet itself, a denylisted or excluded app, or a private browser window) and stages it as a removable composer chip. Sending wraps the agent prompt as a quote from `app — window` (capped at 8,000 characters); the transcript keeps the user's plain text. No Settings toggle and no Accessibility prompt for this alone: without trust, or with nothing selected, there is no chip.
- Agents over ACP (`Chat/ACP/`): `ACPClient` speaks newline-delimited JSON-RPC, `ACPBackend` keeps one process per chat and maps `session/update` onto the chat's events. The agent comes from the catalog in `AgentCatalogData.swift` (generated from the ACP registry) and is chosen in the chat settings. Claude Code, Codex and Pi run through the `.mjs` adapters in `Contents/Resources/acp/` on the user's Node 22+ (or a Bun downloaded on request into `~/.ironpet/runtime`), pointed at the user's own CLI by `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH` or `PI_ACP_PI_COMMAND`. Executables are found on the login-shell PATH. Model choice is stored per agent; threads store the agent id, ACP session id and folder. The chat agent id lives in UserDefaults as `chatAgent` (`ChatAgentPreference`). Pre-ACP builds wrote the same ids under `chatBackend`; when `chatAgent` is missing or unknown and `chatBackend` is a known catalog id, that value is copied into `chatAgent` so an upgrade keeps Claude (or Cursor) instead of falling back to Cursor. The old key is left in place.
- Working directory: frontmost Cursor window (window title matched against `windowsState.openedWindows` in Cursor's `storage.json`) or iTerm session path (AppleScript `session.path`). The chat never switches folder or session by itself, so the detected folder is not applied. Only the user changes them (New Chat, the folder picker, a saved thread, the agent switch). With no folder chosen yet, a "Which project?" picker (recent folders, "No project" → `~/.ironpet/scratch`, or choose a folder) shows and nothing sends until one is picked.
- Approvals: the agent sends `session/request_permission` with the tool call (`kind`, `title`, `rawInput`) and a list of options. A chat answers none of them itself and drops none: each request becomes one card, whatever its kind or the agent's mode. `ApprovalRules.card` writes the title and detail (a command, a file edit with a preview, the plan text of an exit-plan-mode request, an MCP tool and its arguments). The card shows exactly the options the agent offered, in its order and with its labels (`allow_once`, `allow_always`, `reject_once`, `reject_always`, plan approval choices, anything else), and the chosen `optionId` goes back as the reply. An option of a kind ironpet has no name for is still a button. Telegram and the phone have only allow and deny, which pick the agent's `allow_once` or `reject_once` option. Two identical requests get two cards, because the option ids belong to the request that offered them. Requests from background runs follow the same rule, see Background permission requests below. ironpet cannot make an agent ask; an agent that does not send the request runs its tools unprompted.
- Questions: Claude Code only gets its AskUserQuestion tool when the client advertises `elicitation.form`, so ironpet does. The agent then sends `elicitation/create` with a flat `requestedSchema`. `ElicitationForm` (`Chat/ACP/Elicitation.swift`) parses it, `ElicitationCard` draws it (radios for `oneOf`, checkboxes for `items.anyOf`, text fields for the `_custom` Other fields and plain strings, numbers and booleans). Submit replies `accept` with the answers, Skip replies `decline`, and stopping the turn or closing the chat replies `cancel`. A schema ironpet cannot draw (nested objects, arrays of objects, URL mode) is declined and logged. A hidden chat announces the question like an approval. The answered card stays in the transcript.
- Background permission requests: `BackgroundPermissions` (`IronPetCore`, `Chat/ACP`) holds the `session/request_permission` calls of runs that have no chat: background jobs and the `new`, `own` and `fork` sessions of an automation (`AutomationSession.run(permissions:)`). Each request becomes a `Signal` in the alerts list (`permission:<id>`, titled with the job or automation, the tool and its input summary), a bubble with one button per option the agent offered (`Announcer.backgroundPermissionBubble`, agent labels, unknown kinds included), a macOS notification with Allow and Deny, an entry in `chat.approvals()` and `chat.decide` (so the phone shows it with the agent's options and Telegram sends it to the first allowed user with Approve and Reject), and a wait: the agent's reply is held until someone answers. Answering with an option id sends that id back; allow and deny from a client without options pick `allow_once` or `reject_once`. Dismissing the alert refuses the request. The request is not counted in `chat.status().pendingApprovals`, so it never blocks opening a thread. With no answer after `jobs.permissionTimeoutMinutes` (default 10, 1 to 1440), the agent gets its `reject_once` option, or the first `reject_*` option, or a cancel when it offered none, and the run records `permission timed out: <tool>` (a job's task note, an automation's run history). For an automation, `allowedTools` and `disallowedTools` apply first (`ToolRule`): a covered call is allowed with no alert, a disallowed call is refused with no alert, and edits to Ghost's memory files are refused. A request for a read, a memory-note edit, a read-only MCP tool or one of ironpet's own tools is allowed without an alert. Automation `main` runs in the open chat and shows cards there. The `{{item.*}}` read-only prompt session and voice mode have no one to ask and refuse what is not a read.
- Permission mode: the chat settings show a Mode picker with exactly the modes the agent advertises in `session/new` (`modes.availableModes`, with the agent's names), for example Claude Code's default, acceptEdits, plan, auto and bypassPermissions. ironpet invents no modes. The default is the mode the agent starts in, which is the one the user configured in that agent (Claude Code reads `permissions.defaultMode` from `~/.claude/settings.json`). A chat never moves a session out of it, bypassPermissions included. Picking a mode sends `session/set_mode` at once and stores the id in `UserDefaults` per agent (`chatMode.<agent id>`), so it applies to the next session, a reopened thread, an agent switch back and a restart. A stored mode the agent no longer advertises is ignored. `current_mode_update` keeps the picker in step when the agent changes mode itself (exiting plan mode, say). An agent that advertises no modes shows no picker and its requests all ask. Each session start logs the mode before and after. Jobs and automations have no picker and no pick: they run in the mode the agent starts in, like a chat with no pick. No destructive-command pattern exists anywhere.
- Stop sends `session/cancel` and keeps the process. Threads are kept and reopened with `session/load`; the replayed transcript is ignored because the chat already holds it.
- ACP chat runs set `IRONPET_ACP_RUN=1`; the hook script skips them so they do not show up as external sessions.
- Memory: entity pages and dated claims in `ironpet.db` (Markdown copies on request), learned in the background and through the `memory_*` tools, reach the first turn of each thread. See [Memory](#memory).

## Screen-aware help (milestone 3)

- ⇧⌥⌘G captures the frontmost window, ⌃⌥⌘G a dragged region (also in the pet's right-click menu). Opens quick chat with the image attached. Separately, opening chat with text selected in the frontmost app attaches that selection as context (see Quick chat).
- Screenshots go to `~/.ironpet/screenshots/` (last 30 kept), which is passed as `additionalDirectories` where the agent supports it. Images go as ACP image blocks when the agent advertises `promptCapabilities.image`; otherwise the prompt names the file.
- The app is signed with a local self-signed identity (`scripts/make_signing_identity.sh`, run by `install.sh` when missing) so TCC permissions survive rebuilds. `scripts/uninstall.sh` removes hooks and the login item by running the installed binary with `--uninstall` (which reuses `HookInstaller`), then deletes the app, Keychain item and preferences, and asks before deleting `~/.ironpet` and the identity.
- Needs Screen Recording permission (also unlocks Cursor window titles for workspace detection). No app exclusions.

## Pet states

| ironpet state | Atlas row |
| --- | --- |
| idle | 0 idle, plus look rows 9-10 following the cursor |
| working | 7 running |
| needs input | 6 waiting |
| done | 4 jumping once, then 8 review |
| failed | 5 failed |
| listening | 3 waving once, then idle |
| attentive (voice mode listening) | 8 review, looping |
| dragged | 1 / 2 running right / left |
| sleeping | idle frame 0, dimmed (no row exists); after 10 min with no activity |
| drinking (water reminder) | 11 sipping from a glass, ironpet extra row |
| stretching (stretch reminder) | 12 arms overhead, side stretch, ironpet extra row |

Rows 11-12 are ironpet additions below the Codex v2 layout, so ironpet's sheet is 1536x2704. Atlases without them (Codex pets, older sheets) play the waving row instead.

Reduced motion: frame 0 only. Pet art is loaded from `pet.sprite` in config.json, else `~/.ironpet/pet/spritesheet.{webp,png}`, else the Ghost sheet bundled in the app (generated by `scripts/bundle.sh` with `tools/make_pet.swift`), else a drawn placeholder.

Pet gallery (`App/PetGallery.swift`, `Pet/PetLibrary.swift`): Settings → Pet lists the six sheets `scripts/bundle.sh` generates into `Resources/pets/`, every valid PNG or WebP in `~/.ironpet/pets/` (same name replaces the bundled pet), and a `pet.sprite` that points elsewhere. Invalid files are skipped. Each tile plays idle, waving, jumping and running with the pet's own `AtlasRow` durations. One 15 Hz timer drives all tiles and a 2 s poll of the folder (names, sizes, dates) reloads it; both run only while the General page of the ironpet window is on screen. Reduce Motion shows idle frame 0 and starts no animation timer. Selecting a tile sets `pet.sprite` and renames the pet only if its name is a built-in pet's name or the previous pet's name. "Add from file…" copies a validated sheet into the folder. "Build a new pet" sends `/ironpet-pets <description>` (`PetPrompt`), installing the skill first through `SkillManager` when no agent has it. The skill holds the atlas layout and finds the generator itself, and a test keeps it in step with `AtlasRow`. `skills/ironpet-pets/SKILL.md` is compiled into `BundledSkillsData` like every skill, so Settings → Skills lists it and auto-update keeps installed copies current, opens the chat without calling `prepareForShow`, so the session and folder stay as they are, and sends it in the current thread. `/test/build-pet` triggers it in test mode. OpenAI's built-in pet art is never used or bundled.

Status of milestone 2: built. Threads are saved to `~/.ironpet/threads/` and reopened from the history menu (reopened with `session/load`). Memory is described in [Memory](#memory).

## Additions after v1

- **Agent summaries.** Per turn, the watcher records edited files (Cursor `postToolUse`, Claude `PostToolUse` on edit tools) and the final reply (Cursor `afterAgentResponse.text`; Claude `Stop.last_assistant_message` or the tail of `transcript_path`). The summary is "Edited N files · first sentence of the reply" and is used in done/failed notifications and the session list. Headless cursor-agent sends no reply event, so its summary is files only.
- **Approve from notifications.** Approval notifications (chat hidden) use a category with Allow / Deny actions that call the same `decide` as the chat card; resolving a card clears its notification.
- **Alerts (`Signals/`).** An alert is a `Signal` in `SignalStore`: an id, label, title, subtitle, optional URL, symbol, mood and an optional "Ask Ghost" prompt. Script automations create them with `alert` actions. A new or changed alert gets a bubble (the first script run adds alerts quietly), and the list keeps it until it is dismissed or the script resolves it. The most urgent mood among open alerts sets Ghost's mood and badge. The GitHub and Sentry alerts are script automations (`github-alerts`, `sentry-alerts`, templates in `Automations/AutomationDefaults.swift`), not built-in code, and are not created on a fresh install. The GitHub script runs one `gh api graphql` query per host in `~/.config/gh/hosts.yml` every 2 min (own open PRs with CI rollup and review decision, plus review requests) and keeps each PR's CI and review state in its script state. It alerts on failing CI, changes requested and review requests, resolves them when they clear, and shows a short bubble for CI passed and approved. The Sentry script reads `~/.ironpet/sentry.json` and the Keychain token, queries `is:unresolved firstSeen:-1h` and `is:unresolved is:escalating` with curl, alerts on each issue, and resolves an escalation when it stops. Each alert offers Open, Ask Ghost (prefilled prompt, not auto-sent) and Dismiss.

- **MCP in chat.** Headless cursor-agent loads the user's MCP servers (signed in with `cursor-agent mcp login`). Cursor fires `preToolUse` (`MCP:<tool>`, allowed) and then `beforeMCPExecution` (tool, input, server URL), which ironpet gates; Claude Code tools named `mcp__<server>__<tool>` are gated on `PreToolUse`. Read-only verbs (`get`, `list`, `search`, `find`, `fetch`, `read`, `describe`, `whoami`, `lookup`, `show`, `count`) pass; everything else asks. In a chat every `session/request_permission` for an MCP tool shows a card with the agent's options, and ironpet applies no pattern check; the agent's mode decides which MCP calls it asks about. Sentry: REST API for alert polling, Sentry MCP for "Ask Ghost" investigations.
- **Shared MCP sign-ins (opt-in, `integrations.shareMCPSignIns` in `~/.ironpet/config.json`).** cursor-agent keeps OAuth sign-ins per workspace in `~/.cursor/projects/<slug>/mcp-auth.json` (slug = path with non-alphanumerics as `-`). Before each pet chat run, `MCPAuthSharing` copies every server entry that has tokens (with its client registration) from the most recently modified file into the run's workspace file(s), covering both `/tmp/...` and `/private/tmp/...` slugs. This relies on an internal Cursor file format.
- **Automations (`Automations/`).** Reminders, watchers and scheduled jobs are `Automation` records in `~/.ironpet/automations.json` (trigger `interval`, `daily`, `once`, `poll`, `script` or `stream`; action `bubble`, `prompt`, `shell` or `digest`, none for a script). `AutomationStore` loads and validates the file (unknown keys, bad times, literal secrets and duplicate ids are errors), polls its modification date every 2 s, keeps the last good list when an edit is invalid and shows a bubble naming the problem, and writes `automations.schema.json` beside it. On the first launch without the file, `AutomationMigration` turns `config.json` reminders into three `active` interval automations (water 45, stretch 60, eyes 20, keeping their enabled flags) and, only when they were already on (`integrations.githubAlerts`, or a `sentry.json` present), the GitHub and Sentry alerts into script automations. A fresh install gets the three reminders only, and the welcome window's GitHub tick adds the GitHub automation. A file from an earlier build with `builtin` sources is rewritten to those scripts on load. `AutomationEngine` takes time and idle state through an `Environment`, so tests drive it with a fake clock. Every 30 s `tick()` adds the elapsed keyboard time to each enabled `active` interval unless the system idle time or the gap since the last tick is `idleResetMinutes` (5) or more, which resets them. One is due at its interval, or at 75% of it while a watched agent or Ghost chat is running, and everything at 75% or more goes out in one bubble. Nothing active goes out while the chat is open, an approval is pending or a session needs input. `wall` intervals, `daily` slots (including missed ones after sleep, once) and `once` ignore keyboard time and busy state. A `daily` slot is a wall-clock time (`AutomationEngine.slot(on:hour:minute:)`, `Calendar.date(bySettingHour:)`), so it fires at the set time on a day the clocks change; a time the clocks skip fires at the end of the gap (02:30 becomes 03:00) and one that happens twice fires the first time. A `daily` trigger with `catchUpMinutes` works differently: the engine keeps the last slot it fired per automation (`automation_daily`, migration 410, numbered above every other feature's so a database already past them still gets it) and fires the latest slot at or before now once, if it is newer than the stored one and at most `catchUpMinutes` late (never less than 90 s, three ticks, so 0 means on time only); older missed slots are dropped. Turning it on or changing its trigger stores the latest past slot first, and so does the first launch that finds none stored, so a slot from before that never fires; a later launch catches up a slot missed while ironpet was not running. Done jumps Ghost and Snooze makes the automation due again after `snoozeMinutes`. A `shell` action with `report: chat` goes through `AutomationService.reportShell`, which calls the same `postNotice` as a prompt with `report: chat` (kind `automation:<id>`, so a newer notice replaces an unread one): the text names the automation, the command, the exit code and the last 4 KB of stdout and stderr, exit 0 starts a turn, a failure does not, and output equal to `quiet` posts nothing. A script's `chat` action (`text` up to 64 KiB) uses the same call. `until` (`success` or `once`) and a script's `done: true` end in `AutomationService.deleteAfterRun`, which runs after the run and its report. It deletes only when the stored trigger and action still equal the ones that ran, tells the engine through `keepHistoryOnRemoval` to keep the run history and log, then records a `deleted` line. `reminders.paused` holds all time-based automations; polls keep running.
- **Polls (`Automations/PollEngine.swift`).** A port of the necessary parts of agent-trigger's poll engine: run a shell command or `curl` with a timeout (default 30 s) and a 256 KiB output cap, read items with JMESPath (`items`, `id` and `version` expressions, run in-process by the jmespath.swift package, pinned to 1.0.3 because later versions need Swift 6.2 and CI builds with 6.1; filters such as `[?state=='open']` replace agent-trigger's `where`, and regular expressions are not available), and keep a seen set per automation. The first successful run baselines silently; later runs fire for new ids or a changed `version`. Failed runs never baseline. `cooldownMinutes` drops items that arrive too soon after a fire (recorded as `skipped`). Built-in `github` and `sentry` sources call `GitHubWatcher.poll()` and `SentryWatcher.poll()` on the automation's schedule and report through the alerts list. ironpet does not run, call or read agent-trigger.
- **Database (`Support/Database.swift`).** `~/.ironpet/ironpet.db` is ironpet's common database, on the system `SQLite3` module in WAL mode, opened once by `Database` and passed to the features that use it. It knows no feature. Features contribute ordered `Database.Migration`s (a version number, a name, SQL or a closure); the app passes the combined list to `Database.open`. The runner applies the migrations above `PRAGMA user_version`, each in its own `BEGIN IMMEDIATE` transaction that also stores the new version, so a failing one rolls back and leaves the file at the earlier version. A file from a newer ironpet, or one that fails to migrate, is not touched, and the version is checked before the switch to WAL, so its bytes stay as they were. The app logs it, runs on an in-memory database and says so: `Database.open` returns the reason, the in-memory `Database` keeps it in `unavailableReason`, and `SignalStore.reportIfUnavailable` adds one alert ("ironpet can't open its database", with the reason and the file path) and its bubble. The Tasks section, the Usage tab and the automation log show "Not saved: the database is unavailable" instead of their empty state, and `tasks_*` over MCP and `IronPet tasks` return an error naming the reason. All writes run on one serial queue, each in a transaction. Reads use a second read-only connection on a concurrent queue. Other state stays where it was: `config.json`, `automations.json`, threads and meetings are not in the database.
- **Usage (`Usage/UsageStore.swift`, `App/UsageSettings.swift`).** Migration 100 adds `usage_events`: one row per agent turn or transcription request that ironpet runs itself (chat including Telegram, automation prompts, meeting summaries, voice and meeting transcription), with time, feature, model, and only the numbers the agent or provider reported. Missing numbers stay null and show as a dash. Turn cost is the change in the session's cumulative `usage_update` cost since the last record. After `session/load` with no replayed total, the first total is only a baseline: that turn is priced from its tokens (`Usage/UsagePricing.swift`, listed models only) or recorded without a cost. Migration 101 sets chat rows costing over 20 times their token-implied cost to that value. Agents ironpet only launches or watches record nothing. Rows older than 400 days are deleted at launch and at most once a day after that. Writes go through a background queue. The Usage page in Settings shows Today (charted by hour), 7, 30 or 90 days by feature and model. The chart plots requests, tokens or cost, where cost is the sum of the costs recorded per event and events without one count as 0, with a footnote giving their number. A line above the chart gives today's cost and the range's cost. Hovering a column highlights it and shows a tooltip (`UsageTooltip`) with the bucket's date or hour, each feature with a non-zero value in the chosen metric and the total; an empty column shows no tooltip, and the tooltip flips to the left of the column near the right edge.
- **Automation state (`Automations/AutomationState.swift`).** The first client of the database, with prefixed tables from migration 1: `automation_seen` and `automation_state` (seen sets and poll state), `automation_runs` (the last 20 per automation), `automation_approvals` (SHA-256 of the approved or rejected command or prompt) and `automation_snoozes` (restored on launch). Seen items unseen for 7 days and runs older than 30 days are pruned at launch and on every write, and state of deleted automations is dropped. Definitions never go in the database. Migration 4 adds `automation_logs` (time, duration, outcome, summary, and up to 8 KiB of detail per run), written for every poll and script run and for every service event (reminder fired, shell, prompt). Lines older than `automations.logRetentionDays` (config.json, 14 by default, 1 to 365) are deleted at launch and at most once an hour after that, and each automation keeps at most 2000. `AutomationLogWindow` shows them, filtered by automation or problems only, refreshing every 3 s.
- **Streams (`Automations/StreamEngine.swift`, `StreamProcess.swift`, `EventCoalescer.swift`).** A `stream` trigger runs `command` as `/bin/sh -c` for as long as the automation is enabled and approved, and each stdout line is an event. `StreamProcess` starts it with `posix_spawn` in its own process group (`POSIX_SPAWN_SETPGROUP`, default signals, only fds 0 to 2 inherited, stdin is `/dev/null`), reads stdout and stderr with dispatch sources, and signals the whole group: SIGTERM, then SIGKILL after the grace time (2 s) if any member is left. Children a command leaves behind after it exits are stopped the same way. `StreamEngine` keeps one slot per automation, so a second copy never starts: a changed definition waits for the old process to exit, then starts the new one. It reconciles from `AutomationEngine.set` (file changes, pause, delete), from `AutomationService.approve`, and once from `AutomationService.start`, so nothing starts before the approval check is wired. A stream does not tick. After an exit it restarts with a wait of 1 s doubling to 300 s, reset by a run of 60 s or more; exits, restarts and their reasons go to the history and the execution log (nonzero exits as `failed`). A line goes through `PollExtractor` (one line at a time, mode `lines` by default or `json` with `items`, `id`, `version`), then `when` (JMESPath truthiness, `JMES.truthy`), then the rate limit (20 events a second, counted after the filter), then the seen set (only when `id` is set, kept in `automation_seen`, saved at most every 30 s and when the process exits, capped at 5000 ids; it starts empty on the first run and is not a baseline), then `cooldownMinutes`, then `EventCoalescer`. The coalescer is not stream specific. It holds the newest pending event with a count, fires after `debounceSeconds` of quiet, at most once per `throttleSeconds`, and never while the previous fire's action is running. `AutomationService.handle` passes `Fire.finished`, which a shell or background prompt action calls when it ends; bubbles and chat prompts finish at once. `{{count}}` is the merged count. Lines over 64 KiB, events over the rate and events inside a cooldown are dropped and summarised once a second in the log, and stderr is logged in the same summary, never an event. App quit calls `AutomationService.stop`, which sends SIGTERM to every group, waits up to 2 s and sends SIGKILL, so a stuck child cannot hold up the quit. `automations_get` adds `stream` (`running`, `restarting` or `stopped`) and `lastEvent`, and Settings shows the same on the row. A stream command is risky text (`stream:` plus the command), approved like a shell command.
- **Scripts (`Automations/AutomationScript.swift`).** A `script` trigger runs `poll(state)` in QuickJS (zqqf16/QuickJS-Swift, which vendors the official QuickJS), in the main process, on a background queue. A script automation has no `action` (stored as type `none`, left out of the file). The runtime is created with `enableStdModules: false`, so there is no `std`, `os`, file loader or worker, and no `fetch`, timers or `require`. The prelude module gives the script `sh(command, options)` and `console.log`, which call `HostIO`. A script that needs the network runs `curl` through `sh`. Limits: 32 MiB of memory (`JS_SetMemoryLimit`), an interrupt handler that stops the script after 60 s, 8 `sh` calls per run with each timeout capped at the time left and output capped at 256 KiB, 64 KiB of script, 256 KiB of state, 20 actions. `poll` must be synchronous. It returns `{state, actions}`. The state goes to `automation_script_state`. Each action has a type of `bubble`, `alert`, `prompt` or `suggest_task`, and the engine carries it out (`AutomationService.perform`). The script cannot cause a side effect itself, and there is no `shell` action because a script can already call `sh`. A `bubble` is an `AutomationNotice` (same `id` replaces it). An `alert` becomes a `Signal` of kind `automation` in the alerts list, with its own label, symbol and mood from `severity`. A hash of each alert as last shown is in `automation_alerts`: a new or changed alert notifies, one listed again unchanged is left alone even if the user dismissed it, `resolved: true` removes it, and the first run adds alerts quietly. A `prompt` runs through `AutomationPrompt`. A `suggest_task` (`id`, `title`, `due`, `notes`, `url`) is read by `TaskSuggestion.Draft(action:)` and handed to `TaskStore.suggest(_:automation:name:)` (see Tasks); it never creates a task. A script an agent wrote counts as risky text, so its hash needs approval like a shell command. The validator loads the script once in a sandbox that cannot run commands, and requires a `poll` function.

- **Platform adapters (`Platform/`).** Code that needs the Keychain, a child process, the log, the owner of a pid or the clock goes through one protocol per capability: `SecretStore`, `ProcessSpawner`, `LogSink` (`Log` keeps its name and writes through a sink when it has one), `AppInfo` and `WallClock` (`Clock` is a standard library name). `Platform` holds one adapter of each. `AppDelegate` builds `Platform.mac()` once and hands it to the owners that spawn or read secrets; nothing looks an adapter up globally, and an owner that was not wired holds the `Unsupported` adapter, which throws `CapabilityError.unsupported(capability:platform:)`. `Platform.capabilities` lists which adapters are real. `POSIXProcessSpawner` runs on `posix_spawn` with the same flags the app used before (default signals, empty mask, own process group, and on Darwin nothing inherited but 0, 1 and 2). The Keychain adapter (`Platform/Mac/KeychainSecretStore.swift`) keeps the service and account strings of the items already stored and sets no accessibility attribute, as before. `AdapterBoundaryTests` fails when `SecItem*`, `proc_pidpath`, `sysctl` or `posix_spawn` appear outside their adapter. `RemoteIdentity`'s TLS keychain and `RemoteNetwork` stay Mac code.
- **Mac-only services behind protocols (`Platform/`).** The API facades no longer name the Mac services. `MeetingRecorder` (adapter: `MeetingController`), `CaptureControl` (`CaptureService`), `SpeechOutput` (`SpeechPlayer`, the playing half of reading aloud; `SpeechProducer` is the half that plays nothing), `PetAssets` (`MacPetAssets`, over `PetLibrary` and `ChatBackground`) and `FileIntake` (`FolderFileIntake` is the Foundation-only half, `MacFileIntake` adds image conversion) each have an `Unsupported` adapter and sit in `Platform`. `IronPetAPI.Stores` holds the protocols, and `MeetingsAPI`, `VoiceAPI`, `ScreenAPI`, `PetAPI` and `ChatAPI` take them through their initialisers. `MeetingRecorder` and `SpeechOutput` expose a `ChangeSignal` instead of Combine's `objectWillChange`; the Mac classes feed it from their publisher. `Platform.mac(meetings:speech:capture:)` takes the objects `AppDelegate` already owns; the capture service needs the database, so `AppDelegate` swaps it into `platform.capture` once it exists. `FacadeBoundaryTests` fails when one of the four facades names `MeetingController`, `CaptureService`, `SpeechPlayer`, `PetLibrary` or an AVFoundation or ScreenCaptureKit type.
- **Remaining mixed files behind protocols.** `PresenceSource` (`MacPresenceSource`: idle time, screen lock, wake, mic calls) replaces the CoreGraphics and `NSWorkspace` reads in `AutomationEngine`, `WelcomeBack` and `Presence`. `URLOpener` (`MacURLOpener`) opens the address of a bubble button with the action id `open-url`. `AudioTranscoder` (`MacAudioTranscoder`) decodes Telegram audio. All three sit in `Platform`. `MeetingRegenerator` takes its `SpeakerDiarizing` by injection (`FluidDiarizer` is a Mac adapter, `UnsupportedDiarizer` the default), and `MeetingSummary` and `MeetingKeyCache` hold what it shared with `MeetingController`. `VoiceConversation` listens and speaks through `ConversationListening` and `ConversationSpeaker`, with `useMacAudio()` wiring the real ones. `BoundaryTests.testCoreFilesNameNoMacOnlyAPIs` fails when one of these core files names a Mac-only framework or type.
- **Session rollover (`Chat/AgentTranscript.swift`, `Chat/SessionHandoff.swift`, `ChatSession.rolloverIfDue`).** A thread's `id` is its first agent session id and never changes. `ChatThread.session` is the session it runs on now (nil means `id`), `previousSessions` the ones it left, and `handoff` the context for the next new session. `AgentTranscript` locates a Claude Code transcript at `~/.claude/projects/<cwd with every non-alphanumeric as "-">/<session>.jsonl` (checked against 156 folders on disk), tries the cwd and its real path, and returns nil for any other agent, so those never roll over. After each finished turn, at launch (20 s in) and when an approval or form that held it back is answered, `rolloverIfDue` compares the file with `chat.sessionRolloverMB`. When it is over and the chat has no turn, approval, form or queued message, the chat shows as busy and runs one fixed summary turn on the old session (`SessionHandoff.prompt`, 90 s timeout, tools refused, events kept out of the transcript). On a failure or timeout the summary is built from the first and latest user message and the latest reply. The chat then appends the notice `Started a fresh agent session; earlier history is in memory search.`, adds the old id to `previousSessions`, shuts the agent down and logs old id and size. The next message starts a new session with `resume` nil. Its preamble is the memory preamble with the summary, the last 10 messages and the `memory_search` line inserted before `User request:`, so every new agent session gets the preamble. The `session` event of that turn stores the new id and clears the handoff, and logs old and new id. `AgentTranscript.prunePrevious` deletes a previous session's file when its last write is older than `chat.sessionRetentionDays`; it only reads ids from thread metadata, skips every id some thread still runs on, and runs at launch and after each rollover. A `fork` automation run deletes the file of its own forked session id after it ends, only when the fork succeeded and the id differs from the source. A `prompt` automation with `session: own` uses the same mechanism in `AutomationSession.run`: before a run, when the thread's active session file is over the limit, it runs the summary turn on the old session with a separate backend, then runs the prompt in a fresh session with the preamble, summary and last 10 thread messages. The thread keeps its id and its run count, gets the system line, and records `session` and `previousSessions`. An agent without a known transcript file keeps the earlier rule: a fresh thread after `AutomationSession.ownRunLimit` (50) runs.
- **Configuration (`Support/Config.swift`, `App/SettingsWindow.swift`).** `~/.ironpet/config.json` holds pet name and sprite, hotkeys, reminders and integrations. The file is laid over the encoded defaults before decoding, so it only needs changed keys; values are clamped (minutes ≥ 1, empty name → default). An invalid file yields defaults plus an error shown in Settings, and is copied to `config.invalid.json` before Settings overwrites it. `ConfigStore` (main actor) polls the file's modification date every 2 s; `AppDelegate` re-registers hotkeys and reloads the atlas on change, everything else reads the config where it's used. Hotkeys are Carbon `RegisterEventHotKey` from strings like `cmd+opt+g`; a combination another app holds is reported in Settings, and hotkeys are unregistered while the Settings recorder is listening. Chat agent (`chatAgent`, with a one-shot copy from the pre-ACP `chatBackend` key — see Agents over ACP), model, recent folders and window size stay in UserDefaults as UI state.

- **First run (`App/SetupWindow.swift`).** Shown when setup was never finished or skipped and there is no `config.json` (a config brought from another Mac counts as set up). It offers pet name, hooks per agent (pre-ticked when the tool is detected or ironpet's hooks are already there), launch at login, break reminders and GitHub alerts. Start writes `config.json`, installs the chosen hooks, removes unticked ones left by an older version, and switches chat to Claude Code if cursor-agent is missing. Not now or closing the window writes the default config (no hooks). Hooks are recorded as `integrations.cursorHooks` / `claudeHooks`; on each launch the chosen ones are refreshed, and toggling them in Settings installs or removes only that agent's hooks.

## API layer

Every client reaches the app's state through one in-process API, `IronPetAPI` (`Sources/IronPetCore/API/`). The clients are the ironpet window and its views, `MCPEndpoint`, the `IronPet` CLI, the Telegram bridge and, in a later phase, a remote client. They are equals: whatever one can do, the others can do, and there is one chat and one set of state, not one per client. This is phase 0 of the iOS app. It adds no network listener, pairing or tokens, and the app behaves as before. The [Remote API](#remote-api) is the transport that phase 1 puts in front of it.

- **Only the API touches stores.** A store (`TaskStore`, `SignalStore`, `SessionStore`, `ConfigStore`, `MeetingController` and the others) is held by the API and by the AppKit owner that creates it. A view, an adapter or a CLI handler never calls one. Phase 1 then puts a transport and authentication in front of the API and nothing else changes.
- **Namespaces.** One property per area on `IronPetAPI` (`api.tasks`, `api.automations`, and so on), added as the area moves behind it.
- **Moved so far.** `api.tasks` (`TasksAPI`), `api.automations` (`AutomationsAPI`), `api.alerts` (`AlertsAPI`: list, get, dismiss, dismiss all, ask) and `api.chat` (`ChatAPI`: only `Codable` values, async calls and bus events, so the iOS app can call it as the Mac does. Reads: `status`, `messages`, `message(id)`, `approvals`, `forms`, `queue`, `threads`, `options` (agent, model, folder, permission modes and the current one, sign-in and runtime prompts), `commands` (the slash commands for the open chat's agent, another agent, or a thread's agent, as `name`, `detail`, `hint` and `kind`; unfiltered, so a client fetches it when the user types `/` and does the matching and highlighting itself) and a synchronous `snapshot`. Changes: `send` with an optional origin and files or uploads, `stop` (which hands queued Mac messages back as a draft), `decide`, `answerForm`, `submitForm`, `skipForm`, `openThread`, `newChat`, `setAgent`, `setModel`, `setMode`, `useFolder`, `useNoProject`, and notices. `BoundaryTests` fails when a member of `ChatAPI` names a type that is not `Codable` or is not `async`. The Mac window's own state, the draft, attachments, reply, the slash popup's open state, query and selection, the find bar, file drag and the microphone (recording, transcription and read-aloud stay per device), is in `ChatViewModel` (`Chat/ChatViewModel.swift`), which keeps a copy of the chat current from `ChatAPI` and the event bus. The chat view and the Telegram bridge are two clients. `chat.item` carries the id of the message that was added or changed, and no id means read the transcript again. `chat.state` carries `approvals`, `forms`, `queue`, `draft`, `options`, `commands`, `threads` or `status`, or no id for a turn starting or ending. The replay buffer keeps only the newest `chat.item` per message and the newest `chat.state` per part, so streaming one reply cannot push other events out; live subscribers still hear every event), `api.agents` (`AgentsAPI`: list, get, acknowledge, focus, ask) `api.bubbles` (`BubblesAPI`: list, press, dismiss) and `api.notifications` (`NotificationsAPI`: `list` with `since`, `until`, `source`, `type`, `unreadOnly` and `limit` as a Codable `ListNotificationsRequest`, which returns the matches and the total unread count; `get` with the full description and links; `sources`; `markRead`; `markAllRead`; `unreadCount`). Notifications are created by the owners that show a bubble, so the API has no create call. `NotificationStore` publishes `notifications.changed` on the bus when a row is added (with its id), marked read (with its id), marked all read or pruned (no id). Focusing a session needs the Mac's windows and asking needs the chat, so the app owner supplies `focusHandler` and `askHandler`; without one the call throws `unavailable`. A bubble button, a line in a summary bubble and a tap on the bubble itself all go through `api.bubbles.press`, which looks the control up in the `BubbleActionTable` (bubble id and control id) that the Mac's bubble view also uses, runs it and closes the bubble, so a client that cannot draw SwiftUI can press the same buttons. `Bubble` (`Pet/Bubble.swift`) is plain Codable data: tint and symbol are names, buttons and lines have string ids, and `contentKind` says whether the view draws the standard layout or the live meeting status. The closures live in the `BubbleActionTable`, registered by `BubbleStore.show` from a `BubbleDraft` (a bubble with the closures its buttons run, so a builder cannot list a button without one) and dropped when the bubble goes. `BubbleInfo` is the remote form of a bubble. Both are `ObservableObject`s that forward their store's changes, so a SwiftUI view redraws from the API and never holds the store. MCP tools and the CLI parse loose JSON in `TaskJSON` and `AutomationsAPI.callJSON`, then use the same calls. Approving or rejecting an automation's command is `api.automations.approve` and `reject`, so any client can do it.
- **Calls.** A call takes a `Codable` request value and returns a `Codable` response value, or throws `APIError`. No call returns a store, an image or a closure, so the same call can cross a network later.
- **Errors.** `APIError` has a `code` (`not_found`, `invalid`, `conflict`, `unavailable`, `failed`) and a `message`. A store's own error is wrapped with `APIError.wrap`.
- **Event bus.** `IronPetAPI.events` is the one stream, `APIEventBus`. An `APIEvent` has a `seq` (1, 2, 3, … for the life of the app), a time, a `kind` and an optional `id`. The kinds are `tasks.changed`, `suggestions.changed`, `chat.item`, `chat.state`, `agents.changed`, `alerts.changed`, `bubble.shown`, `bubble.dismissed`, `automations.changed`, `meetings.changed`, `settings.changed`, `pet.mood` and `assets.changed`. An event names what changed and carries no text from the user's data, so a client reads the area again through the API. The bus keeps the last 500 events. `subscribe(after: seq)` first delivers the buffered events above `seq`, then new ones, and sets `gap` when older events were already dropped, which tells the client to read everything again. The stores publish: each has a weak `events` that `AppDelegate` sets.
- **The boundary.** `BoundaryTests` reads the sources and fails when a file that defines a SwiftUI view, `MCPEndpoint`, a tool or CLI adapter (`TaskMCP`, `TaskJSON`, `AutomationMCP`, `ScreenMCP`, `DesktopMCP`, `AssistantMCP`) or `TelegramBridge` names a store type (`TaskStore`, `SignalStore`, `BubbleStore`, `SessionStore`, `AutomationStore`, `AutomationService`, `ConfigStore`, `MeetingController`, `MeetingLibrary`, `VoiceStore`, `UsageStore`, `CaptureStore`, `CaptureService`, `DesktopService`, `ChatSession` and a few more). `PreviewRenderer` is exempt because it builds every store from sample data to render screenshots. The AppKit owners (`AppDelegate`, `PetController`, `IronPetPanel`, `BubblePanel`) create stores and hand them to `IronPetAPI`; they are not clients. A view that needs one setting reads `SettingsAPI.live`, and the Settings pages reach pets and voices through `PetAPI.live` and `VoiceAPI`. `TaskStore.shared` is gone.
- **Tests.** `APITestSupport.makeAPI()` builds the API over in-memory stores, so an area's tests drive it only through the API.

## Two targets

The app is two SwiftPM targets. `IronPetCore` (`Sources/IronPetCore`) holds everything that compiles without UI or a Mac framework: the stores, the API layer, the chat engine, automations, memory, capture storage, the meeting and voice logic, and the platform protocols with their `Unsupported` adapters. `IronPet` (`Sources/IronPet`) holds the UI, the listeners and the Mac adapters (`Platform/Mac/`), and depends on `IronPetCore`. `scripts/extract_core.sh` records how the files were split and lists the files that were edited by hand afterwards.

- **A feature with no UI lands in `IronPetCore`.** Code that needs AppKit, SwiftUI, AVFoundation, Security, Vision or another Mac framework goes behind a protocol in `Sources/IronPetCore/Platform/` and its adapter in `Sources/IronPet/Platform/Mac/`.
- **UI code calls only `IronPetAPI`.** A view, a window model or a listener reads and changes state through the API, never through a store.
- **Access.** Members the Mac target uses are `package`, not `public`. Nothing outside this package sees `IronPetCore`.
- **Imports.** `Tests/IronPetCoreTests/ImportAllowListTests.swift` fails, and names the file and line, when a core file imports a module outside its allow list (Foundation, Dispatch, IronPetKit, JMESPath, QuickJS, and Combine, CryptoKit, Crypto, SQLite3, CSQLite, Darwin, Glibc, FoundationNetworking or NaturalLanguage only inside the matching `#if canImport`).
- **Tests.** A test that touches only core types lives in `Tests/IronPetCoreTests`. Fixtures read with `Bundle.module` live beside the test that reads them. `CISkip`, `TestMemory`, `CaptureTestSupport` and `StubProtocol` exist in both test targets, because a test target cannot see the other's files.

## Remote API

Phases 1 to 4 of the iOS app, Mac side. A paired device reaches `IronPetAPI` over HTTP with its own token. The code is in `Sources/IronPetCore/Remote/` and, for the listener and TLS identity, `Sources/IronPet/Remote/`. It adds no scopes: a paired device can do what the Mac can for the routes below, and the routes grow with later phases.

- **Listener.** `RemoteServer` runs Hummingbird 2 (with its WebSocket module) as two listeners on `remote.port` (47380 by default; never 47321 to 47340, which is the hook server's range). One is plain HTTP on 127.0.0.1, for tests and for a front such as `tailscale serve --bg --https=443 http://127.0.0.1:47380` (checked against `tailscale serve --help` of 1.102, not run against a tailnet). The other is HTTPS on the address `RemoteNetwork.endpoint` works out from `remote.address`, with the certificate of `RemoteIdentity`. Its TLS is Network.framework's: the listener runs on `NIOTSEventLoopGroup` with `TSTLSOptions`, so the app bundles no TLS library (swift-nio-ssl alone would push the executable over the 60 MB check in `scripts/check_adapters.sh`). Network.framework takes the key only as a `SecIdentity`, and macOS makes one only from keychain items, so `RemoteTLSKeychain` creates a keychain file with a random password in the temporary folder at each start, imports the key (as SEC1, the EC format `SecItemImport` reads) and the certificate, and deletes the file when the listener stops. A new keychain locks after five minutes and on sleep, and a locked one fails every handshake, so the keychain is created with `lockOnSleep` off and no lock interval, and a 500 ms timer (`keepUnlocked`) unlocks it with the stored password if something else locks it. File names carry the process id (`ironpet-remote-<pid>-<uuid>.keychain-db`), and `removeStale` deletes files of dead processes at each start. Because the running build imports the items itself, no Keychain prompt appears, also after an update with a new ad-hoc signature, and nothing is added to the login keychain or the search list. Both listeners run on Network.framework: with a plain socket on loopback, Network.framework refused to bind the network address while a connection to the old loopback listener was still closing, which a restart after a rotation or an address change hits (`testTheListenerMovesWhileAConnectionIsStillOpen`). Network.framework waits for a missing address instead of failing, so `start` checks the address against the interfaces first and gives up after five seconds. Nothing binds 0.0.0.0, and a typed `0.0.0.0` or `127.x` address is ignored. Without a usable address, or with a front URL as the address, only the loopback listener runs. If the address is 127.0.0.1 itself, the HTTPS listener takes it alone (tests do this, because a sandbox often cannot connect to the Mac's own LAN address). REST and the event socket share each port. It is off by default (`remote.enabled`). `RemoteController` watches `settings.changed` on the bus, so a change in Settings → Devices, a hand edit of `config.json` or the settings API starts, moves or stops it. It also restarts the listeners when the chosen address changes or when the served certificate is no longer the identity's. Turning it off closes both listeners and every socket. Tokens stay valid. The server never trusts the connection: loopback gets no exemption. A bind to a network address can make macOS ask whether ironpet may accept incoming connections. `EventServer` (47321) is unchanged and stays on loopback.
- **Network address.** `RemoteNetwork.interfaces()` reads the IPv4 addresses of interfaces that are up (`getifaddrs`), without loopback and 169.254.x. `addresses(from:magicDNS:)` orders them: Tailscale (100.64.0.0/10) first, then `en*`, then everything else, each shown as `<ip> (<interface>)`. When `tailscale status --json` (found at `/usr/local/bin`, `/opt/homebrew/bin` or the Tailscale app, two second limit) gives `Self.DNSName`, that name is listed after the Tailscale addresses and binds the first Tailscale address. `remote.address` is empty for the first line, one line's value, an IPv4 address (bound even if not listed), a URL starting with `http://` or `https://`, or a bare host name (taken as `https://<name>`). A URL or host name is a front: loopback only, no certificate pin. The refresh button re-reads the interfaces. An older `remote.baseUrl` moves to `remote.address` when the config loads. `remote.machineName` (default: the Mac's name) appears in the Allow bubble and over the device list.
- **Gate.** `RemoteGate` runs first on every request. It refuses headers over 64 KiB (431) and bodies over 1 MiB (413, 20 MiB for `POST /v1/uploads` and `POST /v1/settings/background`), checks the bearer token, applies the rate limits, adds `Cache-Control: no-store` and writes one access log row. Only `POST /v1/pair` and `GET /v1/pair/:id` work without a token.
- **Errors.** `{"error":{"code","message"}}`. Validator and `APIError` messages pass through unchanged. A failed token is `401` with the fixed message `unauthorized`.
- **Pairing.** Settings → Devices shows a code as soon as the remote API is listening (128 random bits, single use, valid five minutes, stored as SHA-256), without a button press. The page makes the code when it opens and closes it when it closes. Regenerate code replaces it, and five wrong codes stop automatic regeneration until you press the button. The QR code and the copyable link are `ironpet://pair?u=https://<ip>:47380&c=<code>&f=<certificate fingerprint>`. `f` is the SHA-256 of the DER certificate that the HTTPS listener presents. The phone pins it and refuses any other. For a front address the link is `ironpet://pair?u=<front URL>&c=<code>` with no `f`, because the front has its own certificate. This replaces the Ed25519 key and the signed pairing answer of the first version. A pinned TLS channel makes the signature redundant, and `POST /v1/pair` no longer returns `public_key` or `signature`. The certificate is a self-signed P-256 certificate (CN `ironpet`, ten years, not a CA, server authentication), encoded by hand in `SelfSignedCertificate` and signed with CryptoKit, and it and its key are kept in `~/.ironpet/remote/identity.key` (mode 0600). A key file of the older format is replaced. The phone calls `POST /v1/pair` with `code`, `device_name` and an optional `device_public_key`. A good code answers `202` with `pairing_id`, `secret` and `expires_in`. A bubble asks "Allow <device> to connect to <machine name>?" (Allow and Deny, the same table as every bubble). The phone polls `GET /v1/pair/:id` with the header `X-Pairing-Secret`. The answer is `pending`, `denied`, `expired`, or `allowed` with a 256-bit token (`ipt_` and base64url) exactly once, then `410`. Only the token's SHA-256 is stored, and comparison runs over every row without stopping early. A pending request lives in memory only, so a restart drops it.
- **Devices.** `remote_devices` has name, created, last seen and the last `X-Forwarded-For` value, shown as sent and never trusted. `DELETE /v1/devices/me` or Revoke deletes the row, and the next request is `401` and the device's sockets close at once. Revoke all and rotate also makes a new certificate and restarts the HTTPS listener with it, so older fingerprints and tokens stop working.
- **Routes.** `GET /v1/devices/me`; `GET`, `POST /v1/tasks`; `GET`, `PATCH`, `DELETE /v1/tasks/:id`; `POST /v1/tasks/:id/close` (a note is required, as for an agent); `GET /v1/suggestions`; `POST /v1/suggestions/:id/accept` and `/reject`; `GET /v1/task-filters` and `DELETE /v1/task-filters/:id` (the saved quick filters, see Quick filters under Tasks); `GET /v1/events`. JSON uses the keys of the MCP tools (`TaskJSON`: snake_case, ISO 8601). `RemoteTasks` calls `TasksAPI` with the author `remote:<device id>`, which task history records. `POST /v1/tasks`, `PATCH /v1/tasks/:id` and `POST /v1/tasks/:id/close` take an optional `client_id` (a UUID the phone makes) and, on the last two, `base_updated` (the `updated` time of the copy the phone edited). `RemoteTaskLedger` remembers the answer per device and `client_id` for 512 changes of one Mac launch, so a replayed change applies once and gets the first answer. A `base_updated` that differs from the task's `updated` at the second answers 409 `conflict` and changes nothing. An older Mac ignores both fields. `/v1/tasks/tell` and the other areas are later phases.
- **Phase 2 routes.** All go through `IronPetAPI`, in `RemoteResources`, with snake_case keys and ISO 8601 dates. `GET /v1/pet` (name, `mood`, `badge`, `tricks`, `sprite` = `pet.sprite`, `background`, `background_asset`, and `accent` and `accent_dark` as `#RRGGBB` when the user picked a macOS accent colour, absent for multicolour) and `POST /v1/pet/tricks/:name` (`api.pet.perform`, 404 for a name the pet does not know). `GET /v1/bubbles` and `POST /v1/bubbles/:id/actions/:action`. A bubble carries `mac_only`. The Mac marks the bubbles whose buttons decide something only it may decide (`Bubble.macOnly`: a chat tool Allow and Deny, an automation or desktop-control Approve and Reject, Telegram and remote pairing) and the route sends them with an empty `actions` list, and the phone shows "Answer on the Mac". A press on one is 404, as is an unknown action id or a bubble that is already gone. Action ids are the ids the bubble registered (`Bubble.Action.id`), so they live as long as the bubble is shown, and a press runs the closure once and closes the bubble (`api.bubbles.press`). `GET /v1/agents` (`api.agents.list`: sessions that are not idle, the most urgent first, so needs input comes before running before done), `GET /v1/agents/:id` (adds `last_response`), `POST /v1/agents/:id/acknowledge` (`SessionStore.acknowledge`: only done or failed sessions) and `POST /v1/agents/:id/ask`. Agent data is what the hooks reported (summary, edited files, last reply); the route reads no transcript. `GET /v1/alerts`, `POST /v1/alerts/:id/dismiss`, `POST /v1/alerts/dismiss-all` and `POST /v1/alerts/:id/ask`. The two `ask` routes send one chat message through `api.chat.send` with the origin `ios:<device id>`, so it goes into the open chat like a Telegram message, is queued behind a running turn and is not read aloud. The text names the session (agent, workspace, status and summary) or is the alert's own prompt (`Signal.ask`); the phone's tap is the confirmation, where the Mac only prefills its input. The answer appears in the Mac's chat, since the phone has no chat screen before phase 3. `GET /v1/today?kind=brief|recap` returns `BriefBuilder`'s sections and items (`api.today.brief`), each item with a `target` (`type` task, session, alert or meeting, `id`, and the alert's `url`). `GET /v1/assets/manifest` and `GET /v1/assets/:sha256`. Events: `pet.mood` (the mood name is the id), `bubble.shown`, `bubble.dismissed`, `agents.changed`, `alerts.changed` and `assets.changed` come from the stores that already publish them on the bus; the socket sends every bus event.
- **Phase 3 routes (chat).** `RemoteChat` (`Remote/RemoteChat.swift`) calls `api.chat` with the origin `ChatOrigin.ios(device:)` (`client` `ios`, `ref` and `device` both the device id), so the Mac transcript marks the message "iPhone" (`ChatOrigin.badge`) and `ChatSession.start` leaves `turnSpoken` false: a phone turn is never read aloud. There is one chat. The phone writes into the chat that is open on the Mac, and opening a thread or a new chat from the phone changes what the Mac shows.
  - `GET /v1/chat/current`: `thread_id`, `title`, `state`, `running`, `activity`, `folder_label`, `agent` (`id`, `name`), `model`, `notice` (what only the Mac can do: choose a folder, install a runtime, sign in), `items`, `approvals`, `forms` (with `fields`, `answers` and `can_submit`) and `queue`. With `limit` (1 to 200) `items` is the newest `limit` messages, or the `limit` before the message `before` names (an item id), and `has_more` says whether older ones exist; an unknown `before` gives no items. Without `limit` the whole thread comes back, with no `has_more`, as older phones expect. `GET /v1/chat/messages/:id` is one item (404 for an unknown id), for a `chat.item` event. `GET /v1/chat/threads` lists saved threads (`id`, `title`, `folder_label` as the folder's name only, `updated`, `agent`) and `GET /v1/chat/threads/:id` adds `items`, read only.
  - An item has `id`, `kind`, `date`, `origin`, `reply` (`item_id`, `sender`, `text`, `selection`, `from_user`) and kind fields: `text` for `user`, `assistant`, `error` and `tool` (with `ok`); `file_name` and `is_image` for `screenshot` (never its path); `text`, `skipped` and `lines` for `form`. `kind` is an open string. The phone draws a kind it does not know as a plain "unsupported message" row with the item's `text`, so a new kind on the Mac, such as automation system messages, needs no change in the phone's decoding.
  - `POST /v1/chat/current/messages` takes `{text, upload_ids?, reply?: {item_id, selection_text?}}` and answers `{outcome}`: `sent`, `queued`, `to_job` or `needs_folder`. Empty text without uploads is 400. A reply names a user or assistant item that is still in the chat (400 otherwise) and builds the same quote as a Mac reply. `GET /v1/chat/current` also carries `options`: `agents`, `models`, `folders` (the Mac's recent folders, an id is the path), `folder`, `modes` (the permission modes the agent advertises, each `id`, `name` and `detail`, absent when it has none) and `mode` (the id in force). `PATCH /v1/chat/options` takes any of `{agent, model (null for the default), folder, no_project, mode}` and calls the same `IronPetAPI.chat` setters as the Mac's chat settings, so the values persist the same way. It checks every field first and answers 400 for an unknown agent, a model the agent does not offer, or a folder that is not a recent one. Agent, model and folder answer 409 while a turn runs, as the Mac's menus are disabled then; `mode` always applies and must be one of the advertised `modes` (400 otherwise), the same call as the Mac's picker (`api.chat.setMode`). The phone has no mode of its own, and the chat settings sheet shows the agent's list. `POST /v1/chat/current/stop` stops the turn and leaves queued Mac messages for the Mac's own draft. `POST /v1/chat/open/:id` and `POST /v1/chat/new` answer 409 with a plain message while a turn runs or an approval or form waits, before `openThread` could stop the turn, so the Mac chat stays as it was. `POST /v1/chat/approvals/:id` takes `{allow}` and is 404 once the approval is decided, by any client. `POST /v1/chat/forms/:id` takes `{answers}` (a string for a single choice, text or number, a list for a multiple choice, a bool for yes or no, null to clear), `/submit` takes the same and submits (400 while a required answer is missing), `/skip` skips.
  - `GET /v1/chat/messages/:id/file` sends the image behind a `screenshot` message of the open chat as raw bytes (`Content-Type` from the extension, `no-store`). The client names a message, never a path, so the route reads only a file the chat already holds (`RemoteChat.file`). A text file, a message that is not an attachment, an id that is not in the open chat and a file that is gone from the Mac are 404, each with its own message, and an image over 20 MiB is 413. Same device token as every chat route: no token is 401. A saved thread's messages are not in the open chat, so their pictures stay chips.
  - `POST /v1/uploads` takes one file as the raw body, up to 20 MiB, with `Content-Type` and `X-File-Name` (percent encoded), and answers `{id, file_name, stored_name, bytes}`. The file is saved as `<random>-<last path component>` in `remote/files/<device id>/` under `Paths.root`. The id is held in memory, so it works for that device only, once, until the Mac app quits. `RemoteGate` raises the body limit for this route and `POST /v1/settings/background` only; every other route keeps 1 MiB. `POST /v1/settings/background` takes one JPEG, PNG or HEIC image as the raw body (kind read from the bytes, 415 otherwise), imports it through `PetAPI.importBackground` and answers the settings. `PetAPI` serves a copy of at most 2400 px (`PetAssets.phoneBackground`) as `chat.background`.
  - Streaming. The socket sends `chat.item` with the message id and, in `item`, the message as it is when the frame is sent (same JSON as `GET /v1/chat/messages/:id`), so the phone needs no read. A message with a file or a form, or with text over 16 KiB (`RemoteChat.maxInlineTextBytes`), goes without `item`, and the phone reads `GET /v1/chat/messages/:id` instead. `RemoteEventThrottle` lets one `chat.item` per message through per 100 ms and always sends the last one after the stream pauses, so the final text is never lost. Other events and `chat.item` without an id pass at once. A `chat.state` with the id `approvals` or `forms` tells the phone to drop a card that another client answered. An older phone ignores `item`, and a phone talking to an older Mac gets no `item` and reads the message.
- **Phase 4 routes (automations, meetings, settings).** `RemoteAutomations`, `RemoteMeetings` and `RemotePhoneSettings` are thin adapters over `IronPetAPI`; the DTOs are Codable types in `IronPetKit/PhaseFourModels.swift` that `RemoteWire` encodes. Automations: `GET`, `POST /v1/automations`; `GET`, `PATCH`, `DELETE /v1/automations/:id`; `GET .../history` and `.../log` (200 lines); `POST .../pause`, `.../resume`, `.../run-now`; `POST /v1/automations/request` (`{"text"}`, sent to the chat inside `AutomationAgentPrompts.newAutomation`). The author is `remote:<device id>`, so `AutomationService.update` keeps a user's approval on a schedule change and drops it on a command change, and `reviewApprovals` never auto-approves a `remote:` author. `automation.needsApproval` (id only) fires when the Mac asks for Approve, and no route approves or rejects. Meetings: `GET /v1/meetings`, `GET /v1/meetings/state`, `GET .../:id/summary` and `.../transcript` (`{"id","text"}`, 404 when the file is missing), `POST .../:id/regenerate?mode=summary|full` (202, the rebuild runs on; `state` shows `regenerating` and the errors, a full rebuild without audio is 409), `POST .../:id/ask`, `DELETE .../:id` (Trash), `POST /v1/meetings/stop` (409 with no recording). There is no start route and no audio route, so both are 404. Settings: `GET /v1/settings` returns `RemoteConfig`, a fixed subset in the key names of `config.json`; `PATCH /v1/settings` takes a merge patch whose every leaf must be in `RemotePhoneSettings.allowed`, or `screenCapture.enabled` and `meetings.enabled` set to `false`, else 403 with nothing saved; `GET /v1/settings/pets` and `POST /v1/settings/pet` use ids that hash the sheet path; `GET /v1/usage?range=7d`.
- **Phase 5 routes (screen captures).** `RemoteScreen` adapts `IronPetAPI.screen`; the DTOs are in `IronPetKit/ScreenModels.swift`. `GET /v1/screen/status` (the `CaptureStatusModel` fields), `GET /v1/screen/changes?since=&until=&app=&window=` (`screen_window` without an id, `since` defaults to `today`), `GET /v1/screen/captures/<id>?root=&role=&text=&depth=` (`screen_window` with an id), `GET /v1/screen/search?q=&app=&since=&until=&limit=` (`screen_search`, limit 1 to 50) and `POST /v1/screen/pause` (`{"minutes": 1...1440}` or `{"until": "tomorrow"}`; no resume). Every route goes through `ScreenAPI.callTool`, so write-time redaction, `CapturePrivacyFilter.filterOnRead` and the tool caps stay in the path. `RemoteDevice.scopes` (migration 543, comma separated column `scopes`) holds `screen`, set only by `RemoteService.setScreenAccess` from the Devices page toggle. `RemoteServer.screenCall` answers 403 without the scope, then counts the request in a per-device sliding window of `RemoteService.screenPerHour` (200) and answers 429 with `Retry-After` for the next one; a refused request is not counted. The access log row of the gate is the log entry, and `RemoteStore.reads` counts successful `GET`s under `/v1/screen/` since local midnight for "Screen read N times today".
- **Assets.** `PetAPI.manifest` lists the sheets of the gallery (bundled `pets/` and `~/.ironpet/pets`, a sheet there replacing a bundled one of the same name) as `sprite:<file>`, the sheet the pet shows now as `pet.sprite` (the lookup of `Atlas.loadDefault`: `pet.sprite`, then `~/.ironpet/pet/spritesheet.{webp,png}`, then the bundled Ghost) and a custom chat background as `chat.background`, each with `sha256`, `bytes`, `content_type` and, for a sheet, `width` and `height`. A sheet that is not 1536 wide and 2288 or 2704 high is left out, as the gallery skips it (the size is read with ImageIO, without decoding). Built-in backgrounds have no file, so the phone gets only their id. `GET /v1/assets/<sha256>` serves the file named by the hash, with `ETag: "<sha256>"` and `Cache-Control: private, max-age=31536000, immutable`, and answers 304 to a matching `If-None-Match`. It is the one route that is not `no-store`: the files hold no personal data and a hash names its bytes for good. A hash that is not in the manifest is 404, so the route reads no path a client names. `assets.changed` fires when `pet.sprite` changes through `PetAPI.select`, when the custom background is picked or dropped, when one is imported and when the folder signature changes (the 30 second check).
- **Event socket.** `GET /v1/events?since=<seq>` upgrades to a WebSocket and needs the same token. It sends `{"kind":"hello","seq":n}`, then `APIEvent` values (`seq`, `at`, `kind`, `id`). With `since` it replays the buffered events above it. When the bus no longer holds them, or `since` is from an earlier launch, it sends `{"kind":"resync","seq":n}` and the client reads everything again. The hello carries the launch's `epoch` (`APIEventBus.epoch`) and the capability `events.resume`. A phone that passes `since` and `epoch` then gets the missed events without throttling, in order, followed by `{"kind":"resumed","seq":n,"replayed":k}`, and reads nothing again. The bus holds 500 events. `EventConnection` saves the last `seq` and `epoch` through `DefaultsResumeStore`, so a restart of the app resumes too (unpairing, a 401 and pairing again call `DefaultsResumeStore.clearAll`), and signals `.resumed` or `.resync`; against a Mac without `events.resume` it signals `.connected` as before. The Mac logs `events resume_from=K replayed=N` (category `remote-resume`). The first frame also lists `capabilities`, and `chat.send` in it means the phone may send a `chat.send` frame with a `client_id` and gets a `chat.ack` with the same id (`docs/protocol.md`, "Over the remote event socket"). `RemoteSendLedger` remembers the last 512 client ids for each device, so a resend over the socket or HTTPS creates one message. The phone keeps a typed message it could not send (no network, Mac asleep, relay down) in `FileOutboxStore`, one JSON file in Application Support named by a hash of the device token and left out of backups. `ChatModel.flushOutbox` sends the waiting messages in order on `connected`, `resync` and `resumed` (after the replayed events), stops at the first one that cannot reach the Mac, fails one that waited over 24 hours or that the Mac refused, and the outbox holds at most 100. A voice message or a message with photos waits too: the bytes are kept in a `.files` folder beside the JSON file, a saved recording is transcribed through a `draft` voice stream, and the phone then sends the text with the same client id. The library pings every 20 seconds and closes a socket whose previous ping is still unanswered at the next one, which is 20 to 40 seconds of silence, not two full misses.
- **Client sessions.** `ClientRegistry` (`Sources/IronPetCore/Clients/`) holds one `ClientSession` for each connected client: device id, name, kind (`mac`, `ios`, `cli`, `windows`), capabilities, `lastInputAt`, subscriptions and connection. `AppDelegate` registers the Mac as the in-process local client before the automation engine starts, with one capability for each real `Platform` adapter (`Platform.clientCapabilities`) plus `desktop`, and registers again when screen capture or desktop control attaches. An open event socket is a session of kind `ios` for the paired device, and closing it, or revoking the device, ends it. The socket also takes one request, `session.hello` (`docs/protocol.md`, "Handshake"), and refuses every other method. `SessionPresence` is the `PresenceSource` that `AutomationEngine` and `WelcomeBack` read: the idle time is the most recent `lastInputAt` of a desktop client, and the Mac's own session gets it from the `MacPresenceSource` adapter on every read. Lock, wake and microphone state still come from the adapter. `CapabilityRouter` sends a server request only to a client that advertises its capability, by the rule in `docs/protocol.md` ("Clients and capabilities"), and fails with `CapabilityError.unsupported` when none does. Nothing in the app calls the router yet. `screen.ingest` (`ScreenAPI.ingest`) stores captures a client redacted itself, through the same privacy gate as the Mac's own captures. `GET /test/clients` lists the sessions in test mode.
- **Voice socket.** `GET /v1/voice` upgrades to a WebSocket with the same token. A device may hold three, counted apart from its event sockets. `RemoteVoice` (core) holds the rules and the server only moves frames. The phone sends text messages `voice.start` (`id`, `format` `pcm_s16le`, `rate` 16000, `channels` 1, `mode` `draft` or `send`), `voice.end` and `voice.cancel`, and binary frames `[0x01][4-byte big-endian seq][PCM]` of 100 ms (3,200 bytes, the last may be shorter). The Mac keeps the first copy of a seq, fills a missing seq with 100 ms of silence and logs it, and refuses a seq of 3,000 or more with `voice.error` (five minutes). On `voice.end` it encodes a WAV, transcribes it through `VoiceAPI.transcribe` (the voice note path, with `SegmentFilter`) and answers `voice.transcript` (`id`, `text`) or `voice.error`. In mode `send` the text also goes to the chat as a message from the device. `tts.enable` (`enabled`) turns spoken replies on for the socket; they are off until the phone asks. When a turn that this device started finishes, the Mac synthesizes the reply through `VoiceAPI.audio` and writes `tts.chunk` (`reply`, `index`, `last`) followed by the binary frame `[0x02][4-byte big-endian index][WAV]` for each chunk, then `tts.end`. Nothing plays on the Mac and `isQuiet` is not asked. `tts.speak` (`item`, a chat message id) reads one assistant message of the open chat the same way, whether or not `tts.enable` is on. The Mac takes the text from its own chat, not from the phone, and answers `tts.chunk` and `tts.end` with `reply` set to the message id. A message that is missing or is not an assistant reply gets `voice.error` and a `tts.end`. A Mac that predates `tts.speak` ignores it. `tts.stop` cancels the synthesis and the chunks not yet written.
- **Rate limits.** Per token 20 requests burst and 5 per second, and 3 sockets. Pairing allows 5 attempts a minute in total, and five wrong codes close every open code. Requests without a valid token to other paths allow 10 a minute in total, then `429` for five minutes with one bubble on the Mac.
- **Tables and log.** `remote_devices`, `remote_pairing` (codes) and `remote_access_log` are migrations 540 to 542 in `ironpet.db`. A database that has them is refused by older builds. The log has time, device id, method, route template (`/v1/tasks/:id`), status, bytes and duration, kept 30 days. It never has a token, code, body, header, path or query. Pairing, refusal, revocation and lockouts go to `activity_events` as `remote.*`.
- **Tests.** `RemoteAPITests` drives a real listener on an ephemeral port through `RemoteServerHarness`, with a fake clock. `RemoteSecureListenerTests` pin the certificate over HTTPS on 127.0.0.1, check the listening sockets with `lsof`, and cover rotation and a front address. `RemoteChatTests` covers the chat routes, the upload limits and the socket throttle. `scripts/remote_check.py` runs the same flow against a `--test-mode` build (with `POST /test/chat/stub` standing in for the agent, so it sends a phone message and an upload and reads the answer back), then moves the listener to the Wi-Fi address and checks the sockets, the pin and, where the Mac can reach its own address, the TLS round trip.

## iOS app

IronPet Remote is the iPhone client of the [Remote API](#remote-api), shipped as IronPet on TestFlight (bundle `dev.ironpet.app`, team `HQWC8SCC63`, built and uploaded by `scripts/ios_testflight.sh`, which the TestFlight workflow runs from GitHub Actions; the Keychain service stays `dev.ironpet.remote`). Phase 1 pairs with the Mac and shows the Tasks tab. Phase 2 adds the Pet, Agents and Alerts tabs and Today. Phase 3 adds the Chat tab. Phase 4 adds the More tab with Automations, Meetings and Settings, phase 5 adds Screen to it, and phase 6 adds voice over `/v1/voice`. The code is in `iOS/` (an XcodeGen `project.yml`, no checked-in `.xcodeproj`) and `Sources/IronPetKit/`, a package target that builds for macOS 14 and iOS 17.

- **IronPetKit.** The wire types (`RemoteTask`, `RemoteSuggestion`, `RemoteEvent`, `RemoteDevice`, the pairing bodies, and for phase 2 `RemotePet`, `RemoteBubble`, `RemoteAgent`, `RemoteAlert`, `RemoteToday`, `RemoteAsset`, and for phase 3 `RemoteChatSnapshot`, `RemoteChatItem`, `RemoteChatRow`, `RemoteChatThread`, `RemoteApproval`, `RemoteForm`, `RemoteQueued`, `RemoteUpload`), `APIPath`, `IronPetClient` (REST), `PairingFlow`, `EventConnection` (the socket), `SharedEventSource` and `PinnedSessionDelegate`. `Atlas`, `AtlasRow` and `PetAnimation` (which row a mood plays) also live here, so the Mac and the phone cut sprite sheets with the same code (`Atlas.load` reads a file or bytes with ImageIO; the Mac's `Atlas.swift` keeps `loadDefault` and aliases the types). The Mac used `NSImage` before; `AtlasSharedTests` checks that both paths give the same pixels for every frame of a Ghost and a Codex sheet. The task and resource routes (`RemoteTasks`, `RemoteResources`) build these types and encode them with `RemoteWire`, so the phone and the Mac share one definition of each body, and `RemoteKitWireTests` checks every route's JSON against golden text and decodes it back into its type. `TaskJSON` still serves the MCP tools and the `IronPet tasks` command. `ModelsTests` decodes a sample of the Mac's JSON. IronPetCore imports IronPetKit (see Imports above).
- **Tabs.** Pet, Chat, Tasks, Agents and More. More lists Alerts, Automations, Meetings, Screen and Settings (phases 4–5); the tab badge counts alerts and automations that wait for Approve. Device (name, last seen, address, certificate, Unpair) opens from the gear button in the Pet tab's navigation bar, as a sheet. Today (the brief and recap, with a Brief and Recap switch) sits at the bottom of the Pet tab and not on a tab of its own, because the pet's mood, its bubbles and Today answer the same question, what needs me now. A Today item switches to the tab that holds its target (a session also opens its detail); a meeting item opens Meetings behind More, and an alert item opens Alerts there. The More tab shows the alert count as its badge, and the Chat tab shows the number of approvals and questions that wait for an answer.
- **Pet tab.** `PetModel` reads `/v1/pet` and `/v1/bubbles`, syncs assets, and follows `pet.mood` (the event id is the mood), `bubble.shown`, `bubble.dismissed`, `assets.changed`, `alerts.changed` and `agents.changed`. `SpriteView` plays `PetAnimation.row` with the frame durations of the atlas row through `SpriteTimeline`: a one-shot row (done, listening) settles into its follow-up row as on the Mac, and Reduce Motion shows one idle frame. A Codex sheet has no drinking or stretching row, so those moods play waving, as on the Mac. The hero draws the Mac's chat background behind the sprite (`ChatBackgroundPicture`, same as Chat), with the mood on a glass chip; tapping the sprite runs the first trick (light haptic, skipped when Reduce Motion is on). Bubbles, trick chips and Today rows use the same `GlassChrome` as the chat composer (Liquid Glass on iOS 26, material before). A bubble shows its title, text and buttons; a Mac-only bubble shows "Answer on the Mac" instead. Tricks are glass chips from the pet's list. Each pet reload writes a `PetSnapshot` (name, mood, badge) into the App Group `group.dev.ironpet.app` for the Home Screen widget and starts or ends a Live Activity while the pet needs attention (`needsInput`, `failed`, `working`, or a badge). Unpair and a 401 clear the snapshot and end the activity. Mood labels live in IronPetKit (`PetMoodLabel`) so the tab, widget and Live Activity stay in sync.
- **Pairing screen.** A branded hero, numbered Mac steps, Scan QR and paste link, then status cards. Accessibility ids (`scan-button`, `pairing-link-field`, `pair-button`, `pairing-status`) stay the same for UI tests.
- **Widget and Live Activity.** `IronPetWidget` (`iOS/IronPetWidget/`) embeds as `dev.ironpet.app.widget`. The small/medium and Lock Screen accessory widgets read `PetSnapshotStore`; the Live Activity UI shares `PetActivityAttributes` with the app. Updates happen when the phone is open and connected; push is still not in the app.
- **Chat cache.** `GET /v1/chat/current` sends an `ETag` over the exact bytes of its body, with `Cache-Control: no-cache`, and answers `304` with no body to a request whose `If-None-Match` matches. The phone (`ChatCache.swift`, `FileChatCache`) saves each page it takes with its ETag, the newest 50 messages and no live state, and shows that page at launch before the Mac answers. Its read sends the saved ETag, so an unchanged chat costs a 304. A message that changes on the phone clears the ETag, so the next read asks in full, and the saved file keeps the page it was made from. The client bypasses URL caching for this read (`.reloadIgnoringLocalCacheData`), since a cache would turn the 304 back into the cached 200.
- **Event reloads (iPhone).** Each tab model reloads what an event changed once the burst of that kind has been quiet for 300 ms (`EventDebouncer` in `TabModels.swift`), so a replay after a reconnect reads each screen once instead of once per event. `connected` and `resync` still reload at once. Tasks asks for done tasks (`include_done=1`) only while its Done section is open, and closing the section drops them.
- **Assets.** `AssetCache` keeps files in `Application Support/assets/<sha256>`. On launch, on reconnect and on `assets.changed` it reads the manifest and downloads `pet.sprite` and `chat.background` when their hash is not on disk. The gallery sheets are not downloaded (the gallery is a settings screen of phase 4). It checks the SHA-256 of a download and, for a sheet, that `Atlas` accepts it, and drops it otherwise. A hash that the manifest no longer lists is deleted after seven days (listed files are touched on every sync).
- **One socket.** The Mac allows three sockets per device and five screens listen, so `SharedEventSource` opens one `EventConnection` and hands every model its own stream. Each model reloads its resource on `connected` and `resync`.
- **Chat tab.** `ChatModel` reads `GET /v1/chat/current` and follows the socket: `chat.item` with an id and an `item` replaces that message (or adds it at the end) without a read; without `item` it reads the message, one read per message at a time, and runs one more read if events came in meanwhile, and a read that finished after a newer event or a full reload is dropped (a 404 falls back to the whole chat), the phone reads the newest 50 messages (`limit=50`) and keeps the older pages it has loaded; the page before the oldest one loads when the top of the transcript shows (`before`). A `chat.state`, or a `chat.item` for a message the phone does not hold while older pages are loaded, reloads the newest page after 300 ms of quiet; a `chat.item` without an id reloads at once. `resync` reloads the chat, and so does `connected`, unless a read ran in the last two seconds (launch reads once). The transcript has the user's and the agent's messages (inline Markdown through `AttributedString(markdown:)`), tool rows, errors, answered forms and attachments. A photo the phone sent shows a thumbnail, matched by the `stored_name` the upload answered; an image from the Mac loads through `GET /v1/chat/messages/:id/file` (see Chat images below), and a file that is not an image, or an image the Mac no longer has, shows a chip. A kind this app does not know shows as an "Unsupported message" row with the item's text. The transcript uses `defaultScrollAnchor(.bottom)`, so a streamed reply keeps the bottom in view while the reader is there and does not pull a reader who scrolled up. Queued messages sit under the transcript, and Stop shows while a turn runs. The composer has the text field, a plus menu with a photo picker and a file importer, and a send button. Attachments upload first, one request each, then the message goes with their ids; an upload that fails (or a file over 20 MiB) sends nothing and keeps the draft. A long press on a user or assistant message offers Reply, which puts the quote above the composer and sends its `item_id`. The menu of an assistant message also has Select text. It swaps the message's SwiftUI blocks for `SelectableText` (`SelectableText.swift`), where one `UITextView` holds each run of headings, paragraphs, quotes and list items, so a selection spans them; code blocks and tables stay SwiftUI views between the runs. The first text view selects everything and shows its edit menu, whose Ask about this starts a reply that sends `selection_text` with the `item_id` (`ChatModel.reply(to:selection:)`), with the list markers left out of the quote. Selecting ends when the reader taps away. A swipe to the right on a message starts the same reply (`SwipeToReply.swift`): the row follows the finger at 0.55 of its travel up to 72 pt, a reply arrow fades in, a medium haptic fires once the pull passes 44 pt, and the row springs back on release. A pan recognizer on the window drives it, so SwiftUI's drag never competes with the transcript's scroll. It begins only for a drag that goes right, is more than twice as wide as it is tall and starts at least 28 pt from the left edge (the edge belongs to the back swipe). A drag that starts on a view inside a horizontally scrollable `UIScrollView`, which is how code blocks and tables scroll, is left to that view. Saved threads and pending messages have no swipe. While a finger rests on the transcript for 0.25 s (`hidesKeyboardOnHold()`, a long-press recognizer on the window that never cancels a touch) the keyboard hides, so the transcript has finished resizing before the long-press menu lifts at 0.5 s. Approval cards have Allow and Deny, and form cards have the fields, Submit and Skip. A card goes when the next `chat.state` read no longer lists it, whichever client answered. The header shows the pet's face and name, as the Mac does. One three-dots menu holds the session line (title and "Claude Code · folder · Done"), Find in chat, Chat settings and Chats. Chats opens a sheet with New chat and the saved threads. Tapping a thread reads it, and Open on Mac makes it the Mac's chat. A 409 from the Mac (a turn runs, or an approval or question waits) shows the Mac's text in an alert. When the Mac chat needs a folder, a runtime or a sign-in, the screen shows the Mac's `notice` and the phone does nothing about it. Choosing the agent, model, folder or Auto mode, slash commands and push notifications are not in the app.
- **Screen (phase 5).** `ScreenModel` reads nothing until its own `TranscriptGate` (reason "Show screen text") has Face ID or the passcode, locks after five minutes in the background and drops everything on lock. `ScreenView` shows the status with pause buttons (15 minutes, 1 hour, until tomorrow), the change list by window for the last hour, today or three days, a search field and `ScreenCaptureView` for an outline. A 403 shows "Screen text is off for this phone" with where to turn it on. `ScreenPrivacyCover` covers the views whenever the scene is not active, and the views are `privacySensitive`. `IronPetClient` sets `urlCache = nil`.
- **File links (phone).** A file path in a reply is a link on the phone (`ChatFilePaths.detect`, the rules the Mac's `FilePathLinks` shares, with `~/` left for the Mac to expand). The phone cannot see the Mac's disk, so every detected path is a link, and a tap opens a sheet that asks `GET /v1/files/preview?path=` (bearer token, `no-store`, the path in the query so no log keeps it). The Mac (`RemoteFilePreview`) allows only a path inside the open chat's folder, checked after `..` and symbolic links are resolved. Recent folders and the scratch folder are not roots. It refuses `.env*`, `.pem`, `.key`, `.p12` and `id_rsa*` files and anything under `.ssh`, `.aws`, `.gnupg`, `.kube` or `.docker`, with 403 and a message the sheet shows as is. A text file comes back as `text/plain` up to 256 KiB with `X-Ironpet-Truncated: 1` when cut, an image comes back raw up to 20 MiB, and a binary file is 415, a missing file 404 and a folder 400. Tests: `RemoteChatTests`, `ChatFilePathsTests`, `ClientTests` and `ChatFileLinksUITests`.
- **Find in chat (phone).** The Find in chat item in the chat header's three-dots menu opens a find bar above the transcript. It searches what a person or the agent wrote, in the text the rows draw, so a markdown marker is not a match and tool steps, notices, forms and attachments are not searched. Case and diacritics are ignored, and `RemoteChatFind` and `ChatFindText` (`IronPetKit`) hold the rules the Mac's `ChatFind` shares: the ranges, stepping with wrap, keeping the current match as a reply streams in, and the "2 of 5" label. Each match is numbered by message, piece of text (`ChatMarkdown.segments`) and occurrence, so every row highlights its own matches, the current one in orange. Stepping scrolls to the message and opens a long user message that is collapsed. While find is open the transcript does not jump to new content. Tests: `RemoteChatFindTests` and `ChatFindUITests`.
- **Voice (phase 6).** `VoiceModel` (`iOS/IronPetRemote/Voice/`) opens the [Voice socket](#remote-api) when the Chat composer holds to talk. Dictation needs voice notes on the Mac (`VoiceAPI.transcribe`); draft mode fills the composer and send mode posts to the chat. Spoken replies stay off until the phone sends `tts.enable`; then replies to phone-started turns play on the device through `ReplyPlayer`, not on the Mac. ## Record ids

Every record has a public id: its kind's prefix, an underscore and random lowercase hex digits (`task_9f3c1e5a07b2`, `job_…`, `auto_…`, `filter_…`). A new id has 12 digits (`RecordID.newDigits`), so installs that never talk to each other do not make the same id. Ids made before that have six digits, and `RecordID.parse` still accepts six or more. The prefixes are in `RecordKind` (`Support/RecordID.swift`): `screen`, `meeting`, `chat`, `msg`, `task`, `auto`, `run`, `job`, `notif`, `page`, `claim` and `filter`. The digits never encode a title or a time, a new id gets one more digit only when every try collides, and an id is never reused.

- **Where they live.** `record_refs(ref, kind, key)` in `ironpet.db` (`Support/RecordRefs.swift`, migration 551). A ref is created the first time its record is listed or read, and tasks and jobs get theirs in the migration. Automations and filters live in JSON and config, so they are looked up by key the same way.
- **Old ids keep working.** A task's slug, a job's `job-…` id, an automation's id and a filter's id are still the keys, so they resolve to the same record. When two kinds share an old id (a task and a filter with the same slug), `get` says so and asks for the ref.
- **`get`.** The MCP tool `get` (`id`) returns any record: a task, a job, an automation or a filter answers with the tool for that kind, so `get` and `tasks_get` return the same text. A capture (`screen_`, through `screen_window`), a notification (`notif_`), a meeting (`meeting_`), a chat (`chat_`) and a message (`msg_`) answer with a JSON object that has `kind` and `ref`. The readers (`Records/RecordReaders.swift`) go through the owning API, never a store. `get` is read-only and needs no approval.
- **Where refs appear.** `ref` is a field of each task, job, automation and filter; of each capture in `screen_search` and `screen_window`; of each notification in `notifications_list` and `notifications_get`; of each meeting in the meetings list (`MeetingInfo`); and of each chat thread (`ChatThreadInfo`). A message's ref is made when the chat asks for it (`ChatAPI.messageRef`); the chat UI shows it in the next PR.
- **Meetings.** A meeting keeps its folder name as its key. Its id is in `meeting.id` inside the folder, so a database that is rebuilt gets the same id back. The audio and the transcript are not moved or changed.

## Node and agent ids

Every install has a node id, `node_` and 16 random hex digits (`NodeIdentity`, `Support/NodeIdentity.swift`). Migration 560 creates the one-row `node_identity` table and fills it, so a fresh database and an upgraded one both have an id from the first open, and it stays across restarts because it lives in `ironpet.db`. `session.hello` and `node.info` report it with the agent id. `AgentID.default` (`agent_default`) is the one agent until the agent registry exists, and that migration turns it into agent 1.

Every write to shared data records who made it in nullable `node_id` and `agent_id` columns, filled by `Provenance.current(db)` inside the write: `task_items` (the last writer) and `task_events`, `memory_claims` (the writer that created the claim) and `memory_changes`, `automation_runs`, and `notification_items`. Migrations 552 to 555 add the columns. Rows from before have both empty, and readers must treat them as unknown. A database with no `node_identity` table, such as a test that opens one feature's migrations, writes a null node id.

Clicking a suggestion opens a simple page with Add and Skip. A row of quick filter chips (`QuickFilterBar`) sits above the list and the board, with "All" first and selected by default. Picking a chip narrows both views, and the search field narrows the result further. The picked chip id is saved per device in UserDefaults (`QuickFilterSelection`, key `tasksQuickFilter`, an `@AppStorage` in the view), so it survives another section and a relaunch. A saved id with no chip is cleared on appear and shows All. The search text is not saved. A chip's right-click menu has Edit…, Move earlier, Move later and Remove… (a confirmation dialog), and the + menu has Add quick filter… and the same actions per filter. Add and Edit open a sheet with one field, "Describe the filter", and Send. Send passes the prompt to `onTellGhost`, so it takes the same path as "Tell Ghost…": `Create a task quick filter: <text>` for Add, and `Change the task quick filter "<name>" (id <id>, current query <json>): <text>` for Edit, and the chat opens. See Quick filters below. The search field matches a task's title and notes. A List/Board toggle in the title row (`TaskViewMode`, saved in UserDefaults as `tasksViewMode`) swaps the list for `TaskBoardView`, with the suggestions above it. `TaskBoard.columns` (`Tasks/TaskBoard.swift`) groups the tasks for both views, so the list's groups and the board's columns are the same; Done keeps the last 7 days. A card drags with its id as the payload. `TaskBoard.drop` sets the status through `TasksAPI.update`, clears `waiting_on` when a waiting task leaves Waiting on others, closes with `TasksAPI.close` for Done, and returns `needsName` for Waiting on others, after which `TaskBoard.hold` sets `waiting_on` (a done task goes back to the backlog, since a done task never shows as waiting). A card's right-click menu and accessibility actions offer "Move to" for the same drops.
- **Quick filters (`IronPetKit/QuickFilter.swift`, `Tasks/QuickFilters.swift`).** A quick filter is `{id, name, query, order}`: a named boolean query over tasks that the chat agent writes and the UI only picks, removes and reorders. `QuickFilterNode` parses the JSON and evaluates it. It lives in IronPetKit, so the Mac (`TaskItem`) and the phone (`RemoteTask`) share one evaluator through `QuickFilterSubject`. Every node is an object with exactly one key: `{"and": [..]}` and `{"or": [..]}` (non-empty arrays), `{"not": node}`, `{"label": {"key": "value"}}` (equal), `{"labelExists": "key"}`, `{"status": "backlog|in_progress|needs_you|done"}` or a list, `{"waitingOn": "Ana"}` (any case) or `null` for nobody, `{"due": {"before": "YYYY-MM-DD"}}`, `{"due": {"after": "YYYY-MM-DD"}}`, `{"due": "overdue"}` (open, and past due; a plain date is overdue once its day has passed), `{"due": "none"}`, `{"source": "user|chat|meeting|..."}` or a list, and `{"text": "substring"}` (title or notes, any case, accents ignored). A query nests at most 8 levels and has at most 60 conditions. `parse` throws a `QuickFilterError` whose path names the bad node, for example `query.and[1].status`. Example: `{"and": [{"label": {"area": "epic"}}, {"not": {"status": "done"}}]}`.
  - **Built-in chips.** `BuiltInQuickFilters` (`IronPetKit/QuickFilter.swift`) holds chips the app adds itself: they are not stored, cannot be edited, moved or removed, and are never written by the agent. Their ids and names are reserved, so `upsertQuickFilter` refuses them and generates an id that skips them. `TasksAPI.quickFilter(id)` falls back to them, so `tasks_list` and `IronPet tasks list --filter` take `next-actions` too. A filter saved before a chip existed with its id or name keeps working: `TasksAPI.builtInQuickFilters` leaves that chip out, and an edit may keep the name. The first one is Next actions (`next-actions`): `status` backlog, in progress or needs you, and `waitingOn` null. The Mac shows it after All, and the list groups its tasks by context (`NextActions.groups`, `Tasks/NextActions.swift`): the six contexts in order, then "No context", with empty groups left out. The board is not grouped.
  - **Context and area labels.** `context` is one of `mac`, `phone`, `calls`, `errands`, `agent`, `home` (`TaskContext`); `TaskValidator.labels` refuses other values and lowercases the value, so every entry point (MCP, CLI, the phone, the task page) checks it. The task page's Context row sets or removes the label (`TaskEdits.setContext`). `area` names what a task belongs to. The Mac reads `area`, then `project`, for the area shown on a task (`TaskItem.areaLabel`), so tasks filed before the rename still show theirs. Nothing migrates; the rename is read-side only.
  - **Storage.** `tasks.quickFilters` in `config.json` (`Config.Tasks`), with the query kept as JSON (`RemoteJSON`), so a condition a newer build added survives a round trip through an older one, which hides that chip instead of failing. Every change goes through `ConfigStore.update`, so it fires `settings.changed` for the phone and a hand edit of the file is picked up. There is no database migration, and a build without this feature ignores the key. The first save by a newer build and a later save by an older one would drop the filters, because the older build rewrites `config.json` without the key. At most 30 filters; names are unique without regard to case, at most 40 characters, and never "All".
  - **Agent tools.** `task_filters_list`, `task_filters_upsert` (`id` optional, `name`, `query`; the query may be an object or a JSON string), `task_filters_delete` and `task_filters_reorder` (`ids`), served by `TaskJSON.call` like the `tasks_*` tools and listed in `ACPToolCall.ownTaskTools`, so they run without a prompt. `task_filters_upsert` refuses an invalid query with the path of the bad node and stores nothing. A new filter goes last, and an edit keeps its place. `tasks_list` takes `filter` (a filter id) or `query` (JSON, not saved), alone or together (joined with and); with either, done tasks are included unless `status` or `include_done` says otherwise, because the query says what to leave out. The CLI has `IronPet tasks filters|filter-set|filter-delete|filter-order` and `list --filter ID --query JSON`. The tool descriptions carry the query schema, and the bundled `ironpet-tasks` skill has a Quick filters section.
  - **Remote.** `GET /v1/task-filters` answers `{"filters": [...]}` in chip order, and `DELETE /v1/task-filters/:id` removes one (404 when it is gone). Both need the device token, like every route. The phone cannot add or edit; it sends the prompt to the main chat. An older Mac answers 404 and the phone shows no chips. A `settings.changed` event tells the phone to reload.

## Background jobs

Ghost as a front desk: the chat agent and [voice mode](#voice-mode) hand work to background jobs and answer "what's going on" from ironpet's own stores.

- **Model and store (`Jobs/JobModel.swift`, `Jobs/JobService.swift`).** Migration 500 adds `jobs` (id `job-xxxxxx`, title, prompt, folder, agent, model, thread, task, state, last step, summary, error, created, started, ended). States: `queued`, `running`, `needs_approval`, `done`, `failed`, `stopped`, `interrupted`. At launch, jobs that ended more than 30 days ago are deleted and every active one becomes `interrupted` in one `UPDATE` (their in-progress task goes back to `backlog`). In memory: the active jobs and the newest finished ones, 50 in all.
- **Running.** `JobService.start` validates (title 1 to 120 characters, prompt up to 20,000, an existing folder), creates an `in_progress` task with source `agent`, and queues the job. `pump` starts queued jobs, oldest first, while fewer than `jobs.maxRunning` (3, clamped to 1 to 5) hold a process. Each gets its own `ACPBackend` (`JobAgent` protocol, faked in tests) with `usageFeature = .jobs`, the chat's agent and model, and a first-turn preamble: `JobService.instructions` (unattended, no questions, stay in the folder, no pushes or messages unless asked, end with a one-sentence result) plus `MemoryPreamble.build` with the job's prompt as the first message and without the task list rules (`keepsTasks: false`), since ironpet keeps the job's task. Elicitations are declined. Each turn has a 60-minute watchdog that cancels it and fails the job; like a stop, the process is closed if the turn has not ended 5 s after the cancel. Quitting closes every job's process (`shutdownAll`). Events go through `TranscriptRecorder` (shared with `AutomationSession`); the thread is saved under the ACP session id with `ChatThread.job`, and the task gets a `thread` link. The job ends `done` with the first sentence of the reply as its summary (task closed), `failed` (task `needs_you` with the error), or `stopped` (task closed).
- **Approvals.** A request that is a read, a memory-note edit, a read-only MCP tool or one of ironpet's own tools (`ApprovalRules.policy`) is answered with allow. Any other request goes to `BackgroundPermissions` (see Background permission requests), the job moves to `needs_approval`, and it returns to `running` when the last open request is answered. Stopping the job, the end of the turn or quitting resolves its open requests with a refusal. A request that times out is noted on the job's task (`permission timed out: <tool>`).
- **Follow-ups and stop.** `followUp` queues a message for a running job (sent after its turn, same process) or requeues a finished one, which resumes the session (`session/load`) without a preamble; that is refused while the chat runs a turn of its own on the same session (`sessionBusy`). `stop` drops a queued job, or cancels the running turn (`session/cancel`) and denies its pending approvals; later permission requests are denied, and an event that arrives after the stop (the agent was still starting, so the cancel did nothing) cancels again. If the turn has not ended 5 s later the process is closed. A follow-up queued during a turn that fails still runs, since it may be the fix; the job's state is the last turn's.
- **In the app.** `Job.agentSession` maps a job to an `AgentSession` with source `job` ("Background job") under the key `job:<id>`, set through `SessionStore.setJob`: queued and running show as running (detail "Waiting to start" or the last step), `needs_approval` as needs input with "Wants to: …", done and failed as themselves, stopped and interrupted are removed. Hook events with source `job` are ignored, and `sweep` skips jobs. `onAttention` records activity as for any session; a job's needs input shows no session bubble, because the approval bubble covers it. A click on the row, the bubble or a brief item opens the job's thread in the chat (`PetController.onOpenJob`). While the job runs, `ChatSession.jobFollowUp` sends a message typed in that thread to the job instead, and `threadSaved` refreshes the open thread as the job writes it, keeping typed messages the job has not started on yet. A reply goes as its quoted prompt and attachments as their paths, so the chat never starts a second process on the job's session. The job saves its thread when each turn starts and ends. Its prompts carry origin `job` ("Background job" under the message).
- **Tools (`Jobs/AssistantMCP.swift`, routed by `MCPEndpoint` through `AssistantContext`).** `jobs_start(title, prompt, folder)`, `jobs_list(include_older?)`, `jobs_get(id)` (with the last 8 transcript steps), `jobs_followup(id, message)`, `jobs_stop(id)`, `jobs_open(id)` (while the chat runs the turn that asked, the thread opens when that turn ends, since opening a thread replaces the chat's). `projects_resolve(name?)` returns `best`, `matches` and `ambiguous` from `ProjectResolver`: candidates are the front Cursor window's folder (`WorkspaceDetector`; iTerm is not asked, since that is an Apple Event on the main thread), the chat's folder, Cursor's open folders (`storage.json`), the folders of watched agent sessions, recent chat folders and the no-project folder, compared by standardized path (Cursor's URLs end in a slash), missing folders dropped. Names are compared as lowercase letters and digits after dropping filler words ("the", "repo", "project"): same name 3, containment 2 (a name under 4 characters only when it contains the query), same first three letters 1, and a single top score wins. `jobs_start` only accepts a candidate's path. `status_overview`, `status_sessions`, `status_alerts`, `status_today(kind)` and `status_meetings(limit?)` read `SessionStore` (jobs left out), `TaskStore`, `SignalStore`, `BriefSource` and `MeetingLibrary` (with `ActionItems.openItems` of each summary). Everything but `jobs_start`, `jobs_followup` and `jobs_stop` is in `ApprovalRules.ownTaskTools`, allowed only when the call names the ironpet server (`ApprovalRules.plainNamedTools`: a name like `status_overview` could be another server's). The memory tools are `MemoryMCP`'s (see [Memory](#memory)).
- **Job scope.** A job's session gets ironpet's MCP entry with `IRONPET_MCP_SCOPE=job`, so its stdio bridge posts to `/mcp/job`, which leaves `jobs_start`, `jobs_followup`, `jobs_stop` and `jobs_open` out of `tools/list` and refuses them. A job cannot start or steer jobs. `makeAgent` also sets `ACPBackend.mcpCaller` to `job:<id>`, so the memory tools know the call is the job's.
- **Memory.** A job shares Ghost's memory with the chat: the preamble above, and the `memory_*` tools with the job as the source and its folder as the default project. Its thread is indexed for `memory_search` like a chat's, but `MemoryReflector` skips threads with `ChatThread.job`, because their first message is the chat agent's prompt, not the user's.

## Memory

Ghost learns about the user, their projects and the people they work with without being asked, and can recall past conversations. Everything is in `Memory/`. The notes are entity pages and dated claims in `ironpet.db`, which is the source of truth; Export writes Markdown copies that nothing reads back.

- **Entities and claims (`Memory/EntityMemoryStore.swift`, `Memory/EntityMatcher.swift`).** `EntityMemoryStore` is the one `MemoryStore`, and the source of truth for notes. Migration 545 adds the public `page_<hex>` and `claim_<hex>` refs, backfilled; they are random, never encode a title or time, and are never reused. Migration 544 (`Memory/MemoryIndex.swift`, numbered above every migration in the app; the memory tables are first created by 510) adds `memory_entities(id, type, name, aliases, identifiers, mentions)` with types `me`, `person`, `project`, `org`, `tool` and `topic`, `memory_claims(id, entity, text, date, sources, invalid_at, pinned)` and `memory_links(type, from_entity, to_entity, count, first_seen, last_seen, sources)`, and a `claim` column on `memory_changes`. The user's page `me` exists from the start. A claim is one line of at most `MemoryNote.maxLength` (240) characters, shown as `- <text> <!-- yyyy-MM-dd <source> -->`; sources are `chat:<8 chars of the thread>`, `job:<id>`, `meeting:<folder>`, `automation:<id>`, `agent` (an MCP call with no chat running) and `user`. `MemoryNote.clean` collapses whitespace and refuses text that `CaptureRedactor` would redact: a claim with a secret is never saved. `replace(_:with:scope:person:project:source:)` runs in one transaction: a claim with the same text is not added twice (it moves to today and gains the source); otherwise the new claim is inserted and the valid claims it replaces (named by text, never pinned ones, at most `MemoryNote.maxForget` (5), refused above that) get `invalid_at`. Nothing is deleted: an invalidated claim stays in the page's history. `forget` invalidates the claims that contain every word of the query, in `me`, a person or the project, refused for none or more than 5. `undo(change)` reverses one change by claim id and refuses when the claim changed since (the change stays). `setPinned` keeps a claim from being replaced; a replacement is then added beside it. Writes log the change and index the claim after the transaction, never inside it (a nested write would deadlock).
- **Matching (`Memory/EntityMatcher.swift`).** An identifier (a repo key) matches first, then a name or alias of the same type. Two matches are ambiguous and are never guessed: the tools and Alerts ask which one is meant. A first name that several full names start with (`Ana` for "Ana Silva" and "Ana Lopez") is ambiguous too; one that fits a single full name is a page of its own, since nothing says it is that person. Ids are `person:<normalized name>` and `project:<key>`. `ProjectKey.of` keys a project by its git repo: a worktree or clone shares one key from the `origin` remote, read from the config files without running `git`; a folder without a remote keys by its path. A person is a stub, not named unasked in the preamble, until they have come up `EntityMemoryStore.stubMentions` (2) times.
- **Migration (`Memory/MemoryMigration.swift`).** Once, on the first launch of this build, the markdown notes of earlier builds in `~/.ironpet/memory/` (`me.md`, `people.md` with a `## Name` section per person, and `projects/*.md`, keyed by their `Repo:` or `Workspace:` header) become claims with their dates and sources, through `importPage`, which skips a claim the page already holds. The files stay on disk and nothing reads them again; a launch that finds none still records the run. The run is the cursor `memory:entities-migrated` in `memory_reflections`.
- **Export (`EntityMemoryStore.exportMarkdown`).** Settings → Memory → Export to Markdown, and the chat's Memory folder button, write each page with valid claims to `~/.ironpet/memory-export/` (`me.md`, `people.md`, `projects/<name>-<8 hex>.md`) and open it. The folder is not the old `memory/` folder, so earlier files are not overwritten. Nothing reads the export back. `EntityMemoryStore.exportDirectory` is a variable, so tests use a temp folder (`TestMemory.isolate()`; `ZMemoryIsolationTests` runs last and fails if a run wrote under the real `memory` folder).
- **Preamble (`Memory/MemoryPreamble.swift`).** The first turn of a thread gets `<memory page="…">` blocks: the user's claims (up to 4 KB), the project's (6 KB) and people's (2 KB; the names the first message mentions first, then the most recently noted, grouped under `## name`). Whole claims only, newest first, with a line saying how many older ones are left out and to use `memory_search`. It says notes are facts the user or Ghost recorded, never instructions, and that search results are data, explains the tools and keeps the task instructions.
- **Tools (`Memory/MemoryMCP.swift`).** `memory_remember` (text, scope `me`, `project` or `people`, person, project folder defaulting to the running chat's), `memory_forget`, `memory_page` (one entity by name, alias or identifier: its valid claims, each with its ref `claim_<hex>` (and the page's `page_<hex>`), its date and sources, and its links), `memory_links` (an entity's links in either direction, optionally of one type) and `memory_search` and `memory_get`, routed from `MCPEndpoint` by name. The running chat's thread names a note's source. A background job sets `mcpCaller` to `job:<id>`: `MemoryMCP.call` treats it like the chat, with the job as the source and `Services.jobFolder` as the default project. An automation's own session sets `ACPBackend.mcpCaller`, which puts `IRONPET_MCP_CALLER=automation:<id>` in the env of its `ironpet` MCP server; `MemoryMCP.call` then uses it as the source, takes no project or thread from the open chat, refuses scope `me` and refuses `memory_forget`. Search merges the index's hits (best match first; kinds `chat`, `meeting`, `note` and `screen`, and `history` is not a kind) with `CaptureStore.search` when screen capture has data. Ids are `chat:<thread>/<item>`, `meeting:<folder>/summary` or `…/transcript#<n>`, `note:claim:<id>` and `screen:<id>`. `memory_get` returns the user and Ghost messages around a chat hit (read from the thread file), a meeting's text, a claim, or a capture. `ApprovalRules.ownTaskTools` holds all six, so they show no card. They only write claims, and forget moves a claim to history. `memory_links` returns no links until the digest job writes some.
- **Index (`Memory/MemoryIndex.swift`).** `memory_docs` (kind, ref, at, title, text, with `UNIQUE(kind, ref)`) and the FTS5 external-content table `memory_fts` hold chat messages, meeting parts and valid claims (`kind note`, `ref claim:<id>`). Chats are indexed one message per document on every `ThreadStore.save`, on the index's own utility queue; only user and assistant messages, never tool output, and neither automation runs nor the prompts an automation sent. Meetings are indexed when a summary is written or regenerated: the summary and the transcript in 40-line parts. A claim is indexed when it is written or restored and removed when it is forgotten or replaced; `reindex()` rebuilds the claim documents from the database. `memory_changes` (at, file, section, action, note, previous, source, undone, claim) is the change log that Undo and Recently learned read. Embeddings are out of scope; the index is FTS5 only.
- **Memory section (`Pet/MemorySection.swift`, `Memory/MemoryBrowser.swift`).** The window's tenth row, after Automations, with the brain icon (`SharedSymbols.memory`); it gets no ⌘N because only nine are bound. `MemoryBrowser` (Foundation only, in `IronPetCore`) is the read side: `rows` makes one `MemoryRow` per page that has a fact (a page with none is hidden) newest fact day first, with the pinned fact, else the newest, as its summary; `list` applies a `MemoryFilter` chip and the search (name, aliases and identifiers first, then pages that only mention the text in a fact, case and accents ignored) and builds the count label ("4 of 26 people"); `EntityMemoryStore.detail` builds a `MemoryDetail` (facts with the pinned ones first, earlier facts, links grouped by direction and type, and other people pages that share the first name as possible duplicates); `forgetClaim` and `forgetPage` write the same change log as `forget`, so a forgotten fact can be undone from the log. `MemoryNavigation` is the stack of open pages. `MemorySectionModel` holds the filter, the search (applied 250 ms after typing), the stack and the focus ring; the list stays in a hidden layer while a page is open, so filter, search and scroll are as they were after Back. The header is `ListScreen` with `titleView` set to the trail while a page is open. The merge banner on a person page is drawn with its button off, since no merge backend exists. The phone gets the same code through `RemoteMemory` and five routes (see `docs/protocol.md`), and `MemoryModel` and `MemoryView` in `iOS/IronPetRemote` show it under More.
- **Reflection (`Memory/MemoryReflector.swift`).** On by default (`memory.reflect`). This is a user-approved exception to the rule that a new feature that sends data in the background is off by default, for four reasons: text only goes to an agent that already had it (the chat's agent, the summary agent that wrote a summary, the agent that ran an automation); it runs on a cheap model where the agent has one; Settings → Memory has a switch (Learn from chats); and its cost shows as its own Usage feature (`memory`). Each job is read by the agent that already had its text, through `Config.Memory.reader(for:)`: `reflectAgent` nil reads with that agent, a picked agent reads only its own text and skips the rest. `cheapModels` gives Claude Code `haiku`. The hourly digest (`MemoryReflector.digest`, called by `tick` once `memory.digestMinutes` have passed, and once a minute after launch) queues: each chat with unread messages (`unread(in:)`, cursor per thread, automation turns left out); each meeting summary written since the last digest (`pendingMeetings`, set by `meetingSummaryWritten`, read with the agent that wrote it); the tasks whose title, notes or status changed since the last digest (one stamp per task, `task:<id>` cursor, whole tasks only, the newest that fit); the screen captures newer than the `screen` cursor, when `memory.learnFromScreen` is on (`captures()`, newest kept within the input limit, the cursor moves past them all); and each page over `memory.maxClaimsPerEntity` (`Job.merge`, `merge` shows the oldest unpinned claims, at most 40, and takes at most 5 merges). Tasks, screen and merges go to `digestReaderAgent()`, the chat's agent; `reader(for:)` skips them under a picked `reflectAgent` unless it is that agent. An automation's final answer is still read at once (`automationFinished`). Each run is one agent call on a restricted `ACPBackend` in `~/.ironpet/scratch/memory`, with a 3-minute limit; ironpet parses the JSON (`parse`, `parseLinks`, `parseMerges`), refuses by outside rules, and writes through `EntityMemoryStore.replace`, `merge` and `link` (after the notes, so a person the pass named has a page). A name that `ambiguousPeople` says fits more than one person is not written: `post` puts a Signal `memory-ambiguous:<name>` in the alerts, with the candidates and Ask Ghost. A failed run keeps its cursors, so the next digest reads the messages again. A meeting summary whose run failed is queued again by the next digest. On the first launch, `seedIfNeeded` marks existing chats read so the update sends none of them. In test mode `automatic` is off and only `reflectNow` (`/test/memory/reflect`) runs a pass.
- **Settings → Memory (`App/MemorySettings.swift`).** After General. The learning switch, the agent picker (first option "Same as the chat (recommended)", the default; a model picker only once one agent is picked), the digest interval ("Learn every N min", 15 to 1,440), the screen switch ("Learn from the screen", off, needs screen capture on); a button that opens the Memory section; the totals; Export to Markdown, which writes and opens `memory-export/`; the error of the last failed pass under Learning; and Forget Everything (with a confirmation), which drops the queued digest jobs and the answer of a pass in flight (`cancelAll`), deletes the claims, links and their index, the old note files and the `memory-export/` copies, and keeps chats and meetings. `MemoryAPI.live` (the Mac's) serves the Memory section and the chat's Memory folder button; `MemorySettingsModel` holds the API, not the store. Settings → Memory shows settings and totals only: the page lists and the search moved to the Memory section, and Recently learned with its Undo button is gone from the UI (`EntityMemoryStore.undo` and the change log stay). The chat's "Memory folder" button exports and opens the same folder.
- **Test hooks.** `GET /test/memory`, `POST /test/memory/reflect` (the open thread, answers at once; poll until `running` is false), `POST /test/memory/undo` (the Settings Undo) and `POST /test/memory/reset` (forget everything, or `reindex` from the database), test mode only. The opt-in e2e scenario `memory` covers the walk-through.

## Prompts

The prompts Ghost sends to agents on its own live in `Prompts/`. The defaults are the files in `prompts/` in the repo, compiled into `BuiltInPromptsData.swift` by `scripts/gen_prompts.py`, which a test checks against the folder. `PromptStore` copies each default to `~/.ironpet/prompts/<id>.md` on first use. A file the user never edited follows a newer default silently. An edited file keeps the user's text, and `.defaults/<id>.md` records the default it was made from, so a newer default shows as an update with its changed lines (`PromptStore.state`). Reset and "Use new default" restore the default; "Keep mine" stops the notice. `Prompts.render` fills `{name}`-style placeholders in one pass, so a value such as a transcript is never read for placeholders. A required placeholder the user removes is appended, so a run keeps its message. `PromptsAPI` is the only path the UI uses (Settings → Prompts). An automation reads its prompt with `{{prompt.<id>}}`, resolved when it runs, so an edit applies to the next run. The built-in Task review (`AutomationDefaults.taskReview`) is on by default, every 20 minutes, in its own session, reporting to the chat with a reply of NOTHING posted as nothing. Mail and calendar checks (`mail-calendar`, `AutomationDefaults.mailCalendar`) use the same shape every hour and are off until the user turns them on. The task scan's prompt (`task-scan`) is listed too, but the scan is a system automation (see Tasks).

The prompts for the front desk (`front-desk`), background jobs (`job-instructions`), memory reflection (`memory-reflection`) and session handoff (`session-handoff`) are editable the same way. Reflection's note count, input size and timeout (`memory.reflectMaxNotes`, `memory.reflectMaxInputChars`, `memory.reflectTimeoutSeconds`) and a job's turn timeout (`jobs.turnTimeoutMinutes`) are in config.json. The chat's recall budgets, the catch-up window, the note length, the front desk's idle shutdown and fast-model words, the job retention, the automation session limits and run timeout, and the meeting transcript cap are config keys too (see the README's Configuration). The messages ironpet sends to the chat agent about automations (`automation-new`, `automation-fix`, and `automation-cli` for the command-line line) are prompts as well. The system notice wrapper, the voice-mode note and the "Ask" prompts on alerts stay in code, because they are UI text. The 3000-character cut on a failed run's output and the 600-character cut on a job's last reply stay in code too, since they are input limits, not wording.

## Telegram

Opt-in (`telegram.enabled`, off by default). `TelegramBridge` long-polls `getUpdates` (30 s, offset in UserDefaults; a new bot's backlog is skipped) through `TelegramAPI`, which takes the token from the Keychain (`ironpet.telegram`) on every call. Messages from ids in `telegram.allowedUsers` go to `api.chat.send` with the origin `telegram` and the Telegram chat id as its ref, which adds a user item with `origin: "telegram"` to the current chat and never calls `use` or `newChat`; a busy agent queues it and the queue drains when the turn ends. `api.chat.onTurn` reports started, waiting for approval, finished(last assistant text) and failed to the origin that started the turn, and the bridge listens only for turns with the `telegram` origin. Approve and Reject buttons call `api.chat.decide`, the same call as the Mac's buttons. `ChatSession` has no Telegram code, and the bridge sends typing every 4 s and the answer through `TelegramFormat` (Markdown to Telegram HTML, split on converted length, code blocks closed and reopened across parts, plain-text retry on a 400). Pairing: with nobody allowed, a `/start` from a private chat becomes a pending request (max 3) and a bubble. Errors set the status line and back off 2, 4, … 300 s. Uploads: `TelegramMediaStore` picks the largest photo size, documents and videos as files and voice, audio and video notes as voice, refuses over 20 MB before and after `getFile`, and saves under `~/.ironpet/telegram/files/<chat>/<stamp>-<id>/<name>`; messages with a shared `media_group_id` in one poll become one chat message. Incoming work with files runs through one in-order queue so text sent after a download does not overtake it. Voice goes through `TelegramVoice` (AVFoundation to 16 kHz WAV when it can decode, else the raw file with its MIME type) and the Settings → Voice server; the transcript is echoed as `🎙 text` and sent as the message text. Approvals: `ChatSession` emits `approval` and `approvalDecided` for Telegram-started turns, the bridge sends Approve and Reject inline buttons (`a:<uuid>:1|0`), and `callback_query` calls `api.chat.decide`, which is the same `decide` the Mac buttons use; the message is edited with the outcome, whoever answered. Forms: `api.chat.onFormsChanged` tells the bridge that a form opened, closed or got an answer, whoever started the turn, and the bridge reads `api.chat.forms` and shows each new form to every allowed user: a header message with the form's text and a Skip form button, then one message per question (`TelegramFormLayout`; a `<id>_custom` text field joins the select before it, as on the Mac). Single select and boolean questions get one button per option (callback data `f:<form number>:<field index>:<option index>`, `:s` skip, `:d` done, `f:<n>:x` skip form, so it stays under 64 bytes); multi select buttons toggle a `✓ ` prefix by editing the keyboard until Done; text and number questions, and the Other box of a select, are answered by Telegram's Reply to that question's message (a number that does not parse gets an error reply and no value). Each answer goes through `api.chat.answerForm`, and when every question is answered or skipped the bridge calls `api.chat.submitForm`, so the Mac closes the form into the same `ElicitationRecord`. Skip form calls `skipForm`. When the form disappears from `api.chat.forms` without Telegram having closed it, the Mac answered it: open messages are edited to `Answered on the Mac.` (or `Skipped on the Mac.`, or `No longer needed: the turn ended.`) and lose their buttons, and a later tap gets `This form is no longer open.` `scripts/fake_telegram.py` and `scripts/telegram_check.py` run the app against a local fake Bot API (`IRONPET_TELEGRAM_API`, honoured only with `--test-mode`, which also keeps the token in memory).

## Voice notes

Opt-in (`voice.enabled`, off by default). `VoiceController` is one state machine (idle, recording, transcribing) driven by the mic button, the voice hotkey (`hotkeys.voice`, registered only while enabled; `voice.holdToTalk` picks hold-and-release or press-to-toggle, and `RecordingKeys` registers Return and Escape globally only while recording) and the `--test-mode` endpoints under `/test/voice/*`, which feed a WAV file through the same states. `MicrophoneSource` records with AVAudioEngine and converts to 16 kHz mono; `Transcriber` posts the WAV to `{baseUrl}/audio/transcriptions` with `file`, `model` and an explicit `response_format=json` (mlx-audio defaults to `ndjson`). The API key is in the Keychain (`ironpet.voice`), never in config.json. The waveform reads a `LevelBuffer` on its own display-rate timeline, so level updates never re-render the chat. A failed transcription keeps the recording in memory so Retry can re-send it. Recordings are capped at 5 minutes instead of being chunked.

Spoken replies are a separate opt-in (`speech.enabled`, off by default, labelled "Read replies aloud automatically") on the same server and key. The switch governs only automatic reading; the speaker button and Read Aloud menu item show whenever `speech.canSpeak` (a speech model is set) and read with the same model, voice and speed with the switch off. `ChatSession` marks every turn sent from the chat (not from another client or an automation), and when that turn finishes without an error calls `SpeechPlayer.speak` with the last reply, unless `isQuiet` says a meeting is recording or another app holds the microphone (`Presence` over a `MicWatch` that `AppDelegate` keeps polling only while the feature is on, because its first answer is always empty). Dictation apps (Wispr Flow, Siri, macOS dictation) never count as holding the microphone, here or for the meeting call offer (`CallApps.ignoredPrefixes`). A speaker button on each reply, its context menu and `/test/speech/speak` call the same player, which does not check the switch (only the automatic path does). `SpeechText` keeps headings, paragraphs, quotes and list items from `Markdown.parse`, drops code, tables, rules, bare URLs and emoji, splits sentences with `NLTokenizer` and stops at the sentence that reaches 900 characters (about a minute); the first chunk is one sentence and later ones are grouped up to 220 characters. `SpeechPlayer` synthesizes the first chunk, plays it with `AVAudioPlayer` while the next is synthesized, and cancels both on stop. Sending a message, starting a voice note, Esc in the chat and turning the feature off all stop it. `Synthesizer` posts JSON to `{baseUrl}/audio/speech` with `response_format: "wav"`; an empty 200 body is reported as missing audio, because that is what mlx-audio returns when Kokoro cannot load without `misaki`. Settings lists voices from mlx-audio's `GET /audio/voices?model=` and falls back to a text field for servers without it (OpenAI), and the switch turns on only after Preview plays, like the Meetings switch.

## Dictation in other apps

`Voice/DictationController.swift` owns a second `VoiceController`, so recording and transcription are the chat's code, but the chat's voice note state is never shared. `AppDelegate` registers `hotkeys.dictation` (Carbon hot key id 13) only while `voice.enabled` is on, and re-registers whenever the hotkeys change, so a new shortcut works at once. A press while recording stops it. `RecordingKeys` gives Enter and Esc to the dictation recording the same way it does for the chat. The two recorders refuse to start while the other is busy, because they would fight for those keys.

`DictationPill` is the bar: a non-activating `DictationBarPanel` over other apps, placed above the focused field (below it when there is no room, top of the screen under the mouse when the field's frame is unknown). It reads the accent colour the chat uses.

`Voice/DictationInsertion.swift` has the delivery rules as plain types over small protocols, so tests drive them with fakes. The bar reads the focused field's frame when recording starts. `DictationDelivery.deliver` reads the focus again, once, when the transcript is ready, and decides from that read:

- a secure text field (`AXSecureTextField`) gets nothing; the text goes to the clipboard;
- no text field, or Accessibility not trusted, also goes to the clipboard, with a notice;
- a text field gets the text as `AXSelectedText`. When the value can be read, the insertion counts only if the value changed;
- if that fails, the text is pasted with Cmd-V and the saved `PasteboardSnapshot` is restored after 300 ms, unless the pasteboard's change count shows someone else wrote to it.

## Voice mode

Opt-in (`voiceMode.enabled`, off by default; the Settings switch turns on only after `Transcriber` accepts the test clip and `SpeechPlayer.preview` plays one line). `VoiceModeController` registers `hotkeys.voiceMode` (default `cmd+opt+ctrl+v`, hotkey id 10) only while it is on, and ties the pieces to the app.

- **State machine (`Voice/VoiceConversation.swift`).** `@MainActor`, `idle → listening → transcribing → thinking → speaking → listening`, with every dependency injected (microphone, transcriber, speaker, `FrontDeskTalking`, quiet check, phrases), so `VoiceConversationTests` drive it without audio. Speech starting while the pet thinks or speaks is a barge-in: the speaker stops, the front desk's turn is cancelled, and a `generation` counter makes overtaken work drop its result. An utterance that ends while the last one is still transcribing is queued and joined to it. A reply that hasn't come 1.2 s into the front desk's turn gets a filler line ("One sec, checking."). A job update that arrives while the user is talking waits until the utterance is cut. It ends on a short goodbye phrase, Esc (a global `HotKey`, id 11, held only during a conversation), the shortcut, the pill's button, `voiceMode.silenceSeconds` with nothing said (20, clamped 5 to 120), a microphone failure, or `quietReason` (a call or a meeting recording, checked every 2 s; it also refuses to start). "Cancel that" and similar phrases call `JobService.cancelHeldVoiceJob` first and only reach the agent when no job is held. Job updates said during a reply wait until the pet listens again. Pet mood: `attentive` (the review row, looping) while listening, `working` while transcribing or thinking, `idle` while speaking; `PetController.voiceMood` wins over agents, alerts and nudges during a conversation.
- **Hearing (`Voice/VoiceActivity.swift`, `Voice/ConversationMic.swift`).** `VoiceActivity` works on `PCMConverter.level` per frame: speech starts after 0.12 s above `max(0.36, noiseFloor + 0.18)` (the floor is a slow average while nobody speaks), ends after a 0.7 s pause, is dropped under 0.3 s voiced, and is cut at 30 s. While the pet's voice plays, starting takes 0.55 for 0.25 s, so echo the canceller leaves behind does not interrupt. `UtteranceCutter` keeps a 0.35 s lead-in and returns each utterance as a 16 kHz WAV. `ConversationMic` is one `AVAudioEngine` with `setVoiceProcessingEnabled(true)` (other-audio ducking set to minimum), a tap through `AdaptiveConverter`, and the cutter on a serial queue; only start, end and discard events reach the main actor. The pet's voice plays through an `AVAudioPlayerNode` on the same engine (`EngineClipPlayer`, WAV clips decoded in memory and converted to 48 kHz mono), so the echo canceller has the reference signal. A configuration change (another input device, for example) reinstalls the tap and restarts the engine; if that fails, the conversation ends with a notice.
- **Front desk (`Voice/FrontDesk.swift`).** An `ACPBackend` (`FrontDeskAgent`: `JobAgent` plus `prepare` and `startNewSession`) on the chat's agent with `voiceMode.model`, or `FrontDesk.fastestModel` of the chat's model list (Haiku, Flash, mini, fast, lite, as whole words), or the chat's model. `usageFeature = .voiceMode`. The process starts when a conversation starts (`prepare`), stays up between conversations and closes after 10 idle minutes or at quit. Each conversation is a new session in the scratch folder whose first turn carries `FrontDesk.instructions` (spoken style, front-desk rules, no spoken approvals, read back before sending to anyone) and the `me` and `people` notes (`MemoryStore.recall`, `MemoryPreamble.budget`, people the first message names). Permissions: `ironpet` server `jobs_start`, `jobs_followup` and `jobs_stop` are allowed, otherwise `ApprovalRules.policy(auto: false)` decides, and anything it would ask about is denied with a pointer to `jobs_start`. Elicitations are declined. Turns are recorded with `TranscriptRecorder`; user items carry origin `voice` (a mic badge under the message), and the thread is saved with `ChatThread.voice` (a mic icon in the history menu). `finish` starts a new session and, when something was said, passes the thread id to `onConversationEnded`, which `AppDelegate` sends to `MemoryReflector.left`, so the reflection pass reads it at once as it does a chat the user left.
- **Voice scope and held jobs.** The front desk's ironpet MCP entry has `IRONPET_MCP_SCOPE=voice`, so its stdio bridge posts to `/mcp/voice` (`MCPEndpoint.path(forScope:)`), which serves every tool and passes `fromVoice` to `AssistantMCP`. `jobs_start` from there calls `JobService.start(fromVoice: true)`, and `jobs_followup` passes `fromVoice` too: the job is queued and marked as a voice job (in memory only), and `pump` skips it while it is held. The hold lasts until `VoiceConversation` calls `releaseVoiceHolds` (after the pet has spoken its reply, or at the end) plus `voiceHold` (5 s), and at most `voiceHoldLimit` (60 s). A follow-up to a running job is not held; it reaches the job after its current turn.
- **Wispr mode (`voiceMode.listenWith = "wispr"`).** No microphone. The pill becomes the key window (ironpet is activated), so Wispr Flow addresses its dictation to ironpet; a `WisprBridge` of the controller's own reads it and calls `VoiceConversation.receive`, and the chat's bridge pauses meanwhile. No barge-in or pause detection. The app that was frontmost when the shortcut was pressed is activated again at the end. `com.electron.wispr-flow` is in `CallApps.ignoredPrefixes`, so Wispr holding the microphone is not a call.
- **No Voice page.** Voice mode is not a sidebar section. Its controls live in Settings → Voice, and it starts from its shortcut (`hotkeys.voiceMode`). Voice conversations are `voice` threads (`ThreadStore`), listed in Chat's Previous chats menu with a microphone.
- **Voice context and the chat's note (`Voice/FrontDesk.swift`, `Chat/ChatSession.swift`).** The first turn of each voice conversation also carries the newest typed chat (`FrontDesk.recentChat`: the last six user and assistant messages of the most recent non-voice thread, each clipped to 500 characters, within 2,000 bytes, oldest first, inside `<chat>` as notes). Every typed chat turn gets `ChatSession.voiceModeNote` at the end of the prompt the agent receives while `voiceMode.enabled` is on (`ChatSession.voiceModeOn`, wired in `AppDelegate`), so the agent keeps its answers short. The stored message does not change, and the note is at the end, so the cached prefix does not change.
- **Sentence-by-sentence speech (`Voice/ReplySpeaker.swift`, `SpeechText.completeSentences`).** `FrontDesk.reply` passes each streamed `agent_message_chunk` to `VoiceConversation`, which feeds a `ReplySpeaker`. Complete sentences (a line break or a full stop with a trailing space or the end) are said one after another as the reply is written, so speech starts after the first sentence; the last unfinished sentence waits for more text or the end of the reply. Synthesis of the next sentence still waits for the previous one to finish, so there is a short gap between sentences. A cancelled speaker drops any text that arrives later. The speech server's streamed audio was measured and not used: its first bytes came about as fast as a full response, because Kokoro generates faster than real time.
- **Talk key (`VoiceConversation.pressTalk`).** While the pet thinks or speaks, the voice-mode shortcut stops the reply, cancels the agent turn and listens. While listening or transcribing, it ends the conversation. The pill's end button and the shortcut still end it.
- **Voice timings (`Voice/VoiceTiming.swift`).** One `os.Logger` line per step under `com.ironpet` / `voice`, with milliseconds since the utterance was cut: `utterance cut`, `transcribed`, `reply requested`, `first sentence`, `reply received`, `speech started`, `speech finished` and `talk key: interrupted`. No text is logged.
- **Pill (`Voice/VoicePill.swift`).** A borderless floating `NSPanel` above the pet (below it at the top of the screen): state, the last thing heard, and an end button; the pet's animation shows that it listens. Accessibility label "Voice mode: <state>".
- **Spoken job updates.** `JobService.onChange` goes to `VoiceModeController.jobChanged`: a voice job that becomes `done`, `failed` or `needs_approval` is announced once per state when `voiceMode.speakJobUpdates` is on and there is no call, meeting recording or away time (idle past `reminders.idleResetMinutes`). During a conversation the conversation says it; otherwise a `SpeechPlayer` of its own does. The bubbles show as for any job.
- **Test mode.** `/test/voice-mode/start` (`reply` stubs the front desk's answers, `mode` picks `ironpet` or `wispr`) swaps in `SilentMic` and `SilentSpeaker` and treats an utterance's bytes as its transcript; `/test/voice-mode/utterance` (`text`), `/test/voice-mode/end` and `GET /test/voice-mode/state` drive and read it, and `GET /test/jobs` lists jobs with `fromVoice`.

## Screen capture

Opt-in (`screenCapture.enabled`, off by default). `CaptureService` is the master switch: with it off no source, timer, event monitor or permission request exists. With it on, in order:

1. **Triggers** (`CaptureSource`, macOS: `AXCaptureSource`; `CaptureScheduler`). Capture is event-driven. Signals are app activation (`NSWorkspace`), focused-window and title changes (`AXObserver` on the front app, on the main run loop), and global `NSEvent` monitors for key, scroll and click, used as timing only. `CaptureScheduler` is a pure struct with a caller-supplied clock. A signal sets a settle time: 0.3 s for an app switch or window focus change, 0.5 s after the last key, 0.4 s after the last scroll, 0.2 s after a click. A key or scroll pushes its own pending capture back, so a burst makes one capture. Every 10 s with nothing pending, an idle capture fires. Two captures are never closer than 0.2 s. The service arms one timer for the next due time and reads on the `ironpet.capture` utility queue.
2. **Privacy gate** (`CapturePrivacy`, `CaptureFloor`, `CaptureURL`). Swift code no setting can change: pause, lock screen, a fixed app and host denylist (password managers, authenticator apps, loginwindow, HTTP proxies), private browser windows by title, URL scheme and host checks, and URL secret stripping. The user's `excludedApps` list adds to it.
3. **Read** (`CapturePipeline`, `CaptureText`). `readFocusedWindow` walks the focused window's tree into `AXNode` values, within 6,000 nodes or 200 ms, whichever comes first, and takes what it read. A secure text field is read for role and subrole only. A button, menu, toolbar, tab, checkbox or similar control is read for its name and page id, never its children, and `CaptureText.lines` drops it. Every element also reads `AXDOMIdentifier`. The text of static text, headings, text areas and text fields is kept as lines. Chromium and Electron apps get `AXManualAccessibility` so they build their page tree. The page address is the first web area's `AXURL`. There are no per-app parsers.
4. **Screenshot fallback** (`ScreenOCR`). When the walk yields no lines and `screenCapture.ocr` is on and Screen Recording is granted, `ScreenOCR.screenshot` captures the app's largest window with `SCScreenshotManager` into a `CGImage`, Vision's `VNRecognizeTextRequest` reads it, and the image is released. It is never written to a file. With the fallback off, such a window stores nothing. Turning the fallback on is what asks for Screen Recording.
5. **Tree store, blocks and drafts** (`CaptureTree`, `CaptureBlocks`, `CaptureTreeStore`, `CaptureStore.ingest`, tables `capture_window`, `capture`, `capture_fts`, `capture_node`, `capture_block_seen`, `capture_draft`, migration 442). `CaptureTree.prepare` drops hidden elements, keeps role and subrole of a secure field, runs every text through `CaptureRedactor` and `CapturePrivacyFilter.filterOnWrite`, and hashes bottom-up: a node is `["<child hashes>", role, subrole, title, value, description, url, domId]` JSON, its key the first 9 bytes of SHA-256 in base64url (12 characters). Nodes are not compressed: a capture's new nodes are a few KB of mostly unique hashes and short texts, which per-row zstd or LZFSE shrinks too little (LZFSE on a packed capture saved about 40%, and a shared dictionary needs a blob column the database layer does not bind). `capture.root` holds the root hash. A new capture writes only the nodes not stored yet (`CaptureStore.lastNodeWrites`). Reading rebuilds a tree with one query per level. `CaptureBlocks.extract` finds blocks by shape: role Group with subrole DocumentArticle, list items and rows, outermost first. A block's label is its accessible name when that name holds text from inside the block, else a line from its own text (headings by name, texts that most sibling blocks repeat left out, siblings meaning blocks that share a list through any single-child wrappers). `when` is the longest text in the block with a four-digit year. Identity is the page id (of the block, or of a wrapper whose only child it is), else a hash of the text. `capture_block_seen` gets a row when a block is new (not seen in the same window in the last 7 days), edited (same page id, different text) or sent. A capture row is stored only when a block changed. A tree that differs only in the text of input fields stores nothing and updates `capture_draft`, one row per field, keyed by page id, else name, else tree path. When a field empties and a new block holds its text, the draft is `sent` and the block's kind is `sent`; with no match in 120 s the draft is `discarded`. `capture.text`, which `capture_fts` indexes, holds the labels and text of the changed blocks. A window with no blocks, and a screenshot read (which has no tree), is one block, the page, with identity `page`: its text is the lines that are new, found with the line diff: a 64-bit SHA-256 prefix of each line of the last capture (`last_lines`), `CaptureDiff.fresh` with two lines of context, redacted first. A window is keyed by app plus window title, or app plus the page address without secrets and fragment. A window without an address whose title changed is matched to the same app's window seen in the last 30 s that shares at least half of its lines. Prune deletes captures, block rows and drafts past retention (default 30 days), then every node that no remaining capture's root reaches. Migration 442 drops the capture tables and creates them again with this schema, so captures stored before the upgrade are deleted. There is no reader for the old rows.
6. **Tools** (`ScreenMCP`, routed by `MCPEndpoint` with the other `tasks_*` and `automations_*` tools, so every chat agent gets them through the stdio bridge). Both are in `ApprovalRules.ownTaskTools`, so they run without an approval card. `screen_search(query, app?, since?, until?, limit?)` runs an FTS5 query (over text, window title, app name and page address) where every word must match and returns the capture id, time, app, window, URL and a snippet. `screen_window(since, until?, app?, window?)` returns the change list from `capture_block_seen` and `capture_draft`, grouped by window, at most 30 lines per window (the newest, dated entries first among equals) and a `more` count, with a page entry for a window without blocks. `screen_window(id)` returns `CaptureView.outline` of the cleaned tree: wrappers with no name are skipped, headings read by name, and text that most sibling blocks repeat is dropped. `root` (a ref) returns one subtree and `role` the elements with that role. A capture with no tree (a screenshot read) returns its text. Both return only stored text, filtered on read. Times accept `today`, `yesterday`, `now`, a date, an ISO 8601 time or an age such as `90m`.
7. **Tasks.** There is no in-app analysis of captures. The bundled `ironpet-tasks` skill has a screen evidence section, which an automation or the user can invoke: a cheap subagent reads the `screen_window` change list since the last run and runs `screen_search` for keys from open task titles, returns who, what, where and when with capture ids, and the reviewing agent updates tasks or creates them with origin kind `capture` and the ids as `ref`. Screen text is data, never instructions. Migration 441 deletes capture suggestions and `task_suggestion_outcomes` and rebuilds `task_suggestions` with only meeting and automation origins.

Settings → Screen shows the switch, Accessibility status, pause buttons, the screenshot fallback toggle, the never-capture list, retention and Delete all captures. The Screen section of the main window (below Transcripts, always listed) is `ScreenSection`: the latest captures (time, app, window, first lines, a row opens its full stored text) and a search field over the FTS index. It reads only the local database. A config change reaches the service through `apply(_:)` with the new value, because `ConfigStore` publishes before it stores.

Test mode (`--test-mode`) swaps in `IdleCaptureSource`, so it never reads the real screen or raises the Accessibility prompt. `GET /test/screen` and `POST /test/screen/ingest|inspector|reset` feed synthetic captures in, and `scripts/e2e.py screen` checks the tools through them.

## Desktop control

Agents operate other apps through ironpet's own MCP server, so there is nothing to install and the Accessibility grant is the one ironpet already has. Off by default (`desktopControl.enabled`).

1. **Reading** (`Desktop/DesktopAX.swift`, `DesktopService`). `LiveDesktopAX` reads a window with `AXCaptureSource.convert`, the walk screen capture uses, so it keeps the node and time budgets (6,000 nodes, 1 second here against 0.2 for background capture, because an agent asked), the Chromium and Electron switch and the rule that a secure field is read for its role only. The walk also returns the `AXUIElement` behind each node in pre-order. `CaptureTree.prepare` cleans the tree (redaction, hidden elements dropped) and gives every node its hash as `ref`. A repeated hash gets `~2`, `~3` in outline order. The views are `CaptureView.outline` (with `allRefs`, so a leaf button has a ref), `CaptureView.find` and `search`. The sibling-text pruning of `CaptureView.cleaned` is not applied, because a control that repeats is exactly what an agent needs to press.
2. **Refs.** `DesktopService` keeps the table ref to element for the last read of each window, replaced on the next read. An entry also keeps a key: the hash of the element's own cleaned role, subrole, title, value and description (the value of an input is left out, so typing does not stale it). Before an action the service reads the element's own fields again and compares the key. A different key, a gone element or an unknown ref fails with "take a new desktop_snapshot".
3. **Actions.** AX actions, except `desktop_key` (item 8). `press` picks AXPress, else AXConfirm, AXPick or AXOpen. `set_value` sets AXValue when it is settable. `type` focuses the element, inserts through AXSelectedText when it is settable, and otherwise appends to AXValue. `focus` sets AXFocused, or raises a window with AXRaise and AXMain.
4. **Gate** (`DesktopSafety`, `DesktopService.check`). The checks run twice, before the question and after the answer, so an element that changed while the user decided does not run. They are: the app is not ironpet and passes `CapturePrivacy.checkApp` (pause, lock, user exclusions, the hard-coded deny list), the window is not private and passes `CapturePrivacy.check` (address rules for a browser), the element is not a secure field, and the ref is current. A generic verb list (send, pay, delete, submit, buy and forms of them) in the element's name, its value (unless it is an input) or the window title requires an approval. The code names no app, and `DesktopControlTests.testDesktopCodeNamesNoApp` scans the folder like the capture code's test.
5. **Approval.** `DesktopApprovals` shows an `AutomationNotice` with Approve and Reject, the same bubble the automation approvals use, and answers no after 120 seconds. The chat's `ApprovalRules` treat the `desktop_*` tools like any other MCP tool, so they also ask in the normal mode.
6. **Log.** Each attempt that reached a resolved element is recorded as an `ActivityEvent` of kind `desktop.action` (outcome `done`, `failed`, `declined` or `refused`), kept 30 days, and listed in Settings → Screen.
7. **Screenshots.** `desktop_screenshot` reads the window first, so the same rules apply, then needs `CGPreflightScreenCaptureAccess`, takes the window by its window id with ScreenCaptureKit (`ScreenOCR.screenshot`), scales the long edge to 1,600 pixels and returns a PNG as an MCP image content block. It is never written to disk.

8. **Keys and addresses.** `desktop_key` parses lowercase names joined by `+` (`DesktopKeys`), runs the same app, window and password-field checks as the other tools, raises the app when it is not frontmost, and posts key down and key up with `CGEvent.postToPid`, never to a system-wide tap. `DesktopSafety.keyApprovalReason` decides approval: Cmd+Return, Cmd+Q and Cmd+W always ask, and Return or a Cmd combo asks when the focused window title or focused element text has a risky verb. The focus is read again after the answer, and a key that now needs approval but was not asked about is refused. `desktop_open_url` accepts http(s) only, no user name or password, a host that passes `CaptureFloor.checkURL`, and opens through the `DesktopOpener` protocol (named browser, else the frontmost browser, else the default).
9. **Select, check, expand.** `select` finds options live through `AXChildren` (menu items, rows, radio buttons, tabs), opens a popup first, needs one match, and refuses an option whose own label has a risky verb unless the user approved. `check` reads the value, presses only when it differs, and reads it again. `expand` sets AXDisclosing or AXExpanded when settable, else presses a disclosure triangle, else opens or cancels a popup.

Test mode swaps in `IdleDesktopAX` and `IdleDesktopOpener`, so an automated run never touches the real screen.

## Meeting transcripts

Opt-in (`meetings.enabled`, off by default; Settings only turns it on after the voice server answers the test clip). `MeetingController` is one state machine (idle, choosing, recording, finishing, summarizing, done) driven by the pet menu, an optional hotkey (`hotkeys.meeting`, no default) and `/test/meeting/*`. Two tracks are recorded: `MicrophoneSource` (Me) and `SystemAudioSource` (Them, ScreenCaptureKit with `capturesAudio`, `excludesCurrentProcessAudio` and an app-filtered `SCContentFilter`, or all system audio). Both implement `StreamingSource`, so samples are handed on as they arrive. A `TrackRecorder` per track (own serial queue) feeds a `Chunker` (closes at the first 0.5 s of silence after the minimum, hard cut at the maximum) and writes `mic-NNN.wav` / `them-NNN.wav`. It pads a stalled source with silence so both tracks stay on one clock, and chunk offsets are sample counts. Each chunk becomes a job: one request at a time, oldest first, `Transcriber.transcribeSegments` (`verbose_json`, one retry with `json` on a 400 or 422, text-only answers become one segment at the chunk start), failures retried with back-off while recording and tried once more after Stop. `MeetingTranscript` shifts segments to meeting time, sorts both tracks and rewrites `transcript.md` after every job. Silent chunks are not uploaded. The summary runs through `CLIBackend` with `RunRequest.readOnly`, which maps to `--tools ""` for Claude Code and `--mode ask --sandbox enabled` for cursor-agent. ironpet writes `summary.md` from the answer. mlx-audio only returns the full payload for `verbose_json` when it has `segments` or `language`, so Parakeet (which returns `sentences`) comes back text-only there; `sentences` only appears with `response_format=ndjson`.

Regenerate (`MeetingRegenerator`, owned by `MeetingLibrary`) rebuilds a finished meeting from its folder, not through `MeetingController`, which only knows the meeting being recorded. `MeetingFolderScan` lists `mic-NNN.wav` and `them-NNN.wav`, takes each chunk's length from its samples, and adds the lengths of earlier chunks of the same track as the offset, which is how `TrackRecorder` counted them. The start time comes from the folder name (minute) and the first chunk's modification time minus its length (second), used only when it falls in that minute; the app name comes from the old transcript's header. Full mode sends the non-silent chunks one at a time in meeting order through the same `Transcriber`, the same diarizer, `MeetingSpeakerTable` and a final `relink` against the current voice store, so it names voices the way a live meeting does but forgets names typed for voices that are not in the store. A failed chunk, an empty transcript or a failed or empty summary throws before any file is touched. The write is two steps: new text goes to `*.new.md`, then each file is moved to `*.prev.md` (replacing the last one) and its `.new.md` moves into place, undoing the finished moves if one fails. Summary-only mode summarises `transcript.md` as it is, which already holds names from `nameSpeaker`. The summary goes through `MeetingSummaryRun`, the same read-only agent setup as `MeetingController.summarize`. `ActionItems.carryChecked` ticks items of the new summary whose normalised text was ticked in the old one, and `ActionItems.newSuggestions` limits task suggestions (the user's own and the ones they wait on) to items the old summary lacked; `TaskStore.suggest` compares titles with the same normalisation. After a speaker is named, `SpeakerPrompt` shows "Regenerate summary" (`MeetingController.canRegenerateSummary`), which runs summary-only mode. Nothing regenerates automatically.

## Updates

Sparkle 2 (SwiftPM, Mac app target only) updates the app. `UpdateController` (`Sources/IronPet/App/UpdateController.swift`) owns the `SPUUpdater` with the standard user driver, so Check now shows Sparkle's own window with the version and release notes. The rules live in `IronPetCore` (`Updates/UpdatePolicy.swift`) so they run in tests:

- A build with `IronPetDevBuild` in Info.plist (made by `scripts/install.sh`) never creates the updater. Settings shows why. `IRONPET_APPCAST_URL` turns updates back on for a dev build only, pointing it at a local appcast.
- A ready update installs only when no agent turn, voice recording or meeting recording is running. `UpdateController` holds Sparkle's install callback and retries every 30 seconds. The pet shows a blue arrow badge, a bubble and a macOS notification offer Restart now, and clicking the badge installs at once.
- `appcast.xml` carries `ironpet:schemaVersion`, the database schema the build reaches (`AppMigrations.latestVersion`, recorded in Info.plist by `bundle.sh`). An update whose schema is lower than the local database's is refused with a message, because that database would not open (`Database.refuseNewer`).
- Settings live in `config.json` under `updates` (`checkAutomatically`, `installAutomatically`), both on by default. The app writes them to Sparkle at launch and on every change, so Sparkle's own UserDefaults copy is never the source.

Only stable releases are in the feed. A beta channel and the Homebrew cask bump are not built yet.

## Testing

`python3 scripts/e2e.py [scenario ...]` (cursor, claude, modes, picker, iterm, capture, summaries, notification, setup, settings; mcp, sentry, voice, voice-key and meeting only when named) relaunches the installed app with `--test-mode`, which enables token-protected `/test/*` endpoints that drive the same code paths as the UI (show chat, send, Allow/Deny, session jump, capture). It runs real cursor-agent and Claude Code turns, checks files on disk and iTerm state via AppleScript, then relaunches the app normally. Test endpoints do not exist outside `--test-mode`.
