# Security

ironpet runs on your Mac with your user's permissions, watches your coding agents, and can start agents that edit files and run commands. This page lists what it touches and what protects it, so you can decide what to turn on. Nothing outside `~/.ironpet` is changed until you confirm the welcome window on first launch.

## Reporting a vulnerability

Please use GitHub's **Report a vulnerability** button on the repository's Security tab instead of a public issue. You'll get a reply within a week.

## What runs where

- **Local HTTP server.** The app listens on `127.0.0.1` only (port written to `~/.ironpet/port`). Every request has to carry the random 256-bit token in `~/.ironpet/token` (mode `0600`), or it gets a 403. The `/test/*` endpoints exist only when the app is started with `--test-mode`.
- **One in-process API.** The windows, the MCP endpoint, the `IronPet` CLI and the Telegram bridge all reach app state through `IronPetAPI` (`Sources/IronPet/API/`, SPEC.md › API layer). It runs inside the app and opens no listener, socket or file of its own, so it exposes nothing beyond the loopback server above and its token. A client that is not this process can reach it only through that server, and the endpoints on that server are the same ones as before this layer existed. `BoundaryTests` fails when a view, the MCP endpoint, a CLI handler or the Telegram bridge names a store type, so a new client cannot skip the API's validation. Every client has the same access: there is no allow-list of calls for one client.
- **Hooks.** `~/.ironpet/bin/ironpet-hook` is called by the agents you choose to watch (Cursor, Claude Code, Codex, Gemini CLI, GitHub Copilot and Pi), so ironpet can show sessions you started yourself. The welcome window and Settings list only agents found on this Mac, and each is off until you turn it on. Hooks only report status: short timeouts, always exit 0, never block or fail your agents. They no longer approve anything. A chat that ironpet runs sets `IRONPET_ACP_RUN=1` on the agent, and the hook script skips those runs. The hook also forwards five ids when the hosting app sets them (`CMUX_WORKSPACE_ID`, `CMUX_SURFACE_ID`, `T3CODE_THREAD_ID`, `HC_TERMINAL_ID`, `ORCA_TERMINAL_HANDLE`) to the local server, which keeps them in memory with the session so Open can reach the exact tab or thread. No other environment variable is sent. For a herdr session, Open runs `herdr-app do agent.focus --terminal <id>` with the id as one argument and no shell. For Orca, Open runs `orca worktree activate` and `orca terminal switch` the same way, with the folder or handle as one argument and no shell. For cmux, T3 Code, Claude desktop and Codex, Open hands a `cmux://`, `t3code://`, `claude://` or `codex://` link to macOS.
- **Agents over ACP.** Chat talks to the agent over the [Agent Client Protocol](https://agentclientprotocol.com) (JSON-RPC on the agent's stdin and stdout). ironpet starts the agent you pick from your own install, found through your login shell's `PATH`: `cursor-agent acp`, `gemini --acp`, `opencode acp` and so on. Claude Code, Codex and Pi have no ACP mode of their own, so ironpet runs a small adapter (a single `.mjs` file in `IronPet.app/Contents/Resources/acp/`) on your Node 22 or newer. The adapter drives your installed `claude`, `codex` or `pi`, which ironpet passes in `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH` or `PI_ACP_PI_COMMAND`. The app bundle contains no agent and no JavaScript runtime. ironpet declares no `fs` or `terminal` client capability, so agents read and write files and run commands with their own tools, under their own permission settings. It lists an agent in the picker only when its command exists and, for agents with native ACP, answers `initialize` (ironpet starts each one briefly to check).
- **Approvals.** The agent decides when to ask. When it wants to run a tool it may send `session/request_permission`, and the chat shows a card for every request it receives, with exactly the options the agent offered (its labels and order, including "allow always" and plan approvals). ironpet answers none of them itself, drops none, and sends the chosen `optionId` back. The chat applies no destructive-command check: the agent's own permission mode decides what it asks about. The chat settings show a **Mode** picker with the modes the agent advertises in `session/new` and no others. The default is the mode you configured in that agent, `bypassPermissions` included, and ironpet does not move a session out of it. Picking a mode sends `session/set_mode` at once and stores the id per agent in the app's preferences (`chatMode.<agent id>`), so it applies again to new chats, reopened threads and after a restart. Each session start logs the mode the agent reported and the mode it is in now. An agent that advertises no modes shows no picker, and every request it sends gets a card. Telegram and the phone can only allow or deny, which pick the agent's once-only option of that kind. Background jobs and automation sessions (`new`, `own`, `fork`) run in the agent's own mode as well, and a request they send raises an alert instead of a chat card (see Background jobs). A request that ironpet cannot show (the app quit, or the turn was stopped) is answered with a cancel, and an unanswered card waits until you decide or stop the turn.
- **Questions.** An agent can ask you a form through `elicitation/create` (Claude Code's AskUserQuestion, and form requests from its MCP servers). The answers you submit go to that agent and are saved in the chat's thread file in `~/.ironpet/threads`, like the rest of the transcript. A form ironpet cannot draw is declined, and stopping the turn or closing the chat answers an open form with a cancel. ironpet does not advertise URL elicitation.
- **Approval cards depend on the agent.** ironpet cannot force an agent to send `session/request_permission`. An agent that runs a tool without asking, because of its own settings, an allow-list or a "never ask" mode, does so without any card, and ironpet only sees the tool call afterwards. For example, `cursor-agent acp` runs commands on its own allow-list (such as `ls`) without asking and asks for the rest, and with `"approvalMode": "unrestricted"` in `~/.cursor/cli-config.json` (Run Everything) it asks for nothing at all. Check an agent's own permission settings before you rely on the cards in the chat. Task runs check them for you (see Task runs below). ironpet applies no destructive-command pattern anywhere.
- **One download, only when you allow it.** If you pick Claude Code, Codex or Pi and your PATH has no Node 22 or newer, the chat shows a **Download Bun** button instead of failing. Only a click starts the download. ironpet fetches Bun 1.4.4 (about 40 MB) from `github.com/oven-sh/bun`, reads the expected SHA-256 from the same release's `SHASUMS256.txt`, and unpacks the archive only if the checksum matches. It then clears the macOS quarantine flag on that file and keeps it at `~/.ironpet/runtime/bun`. A mismatch or a failed download shows an error and runs nothing. This is the only network request ironpet makes on its own initiative besides the optional GitHub, Sentry and voice features below.
- **Telegram (off by default).** With Chat from Telegram on, ironpet long-polls `api.telegram.org` for the bot whose token you saved in Settings → Integrations, and sends each answer to a Telegram-started message back through the same API, so that text passes through Telegram's servers. Only Telegram user ids in `telegram.allowedUsers` reach the chat; everyone else is ignored. With nobody allowed, a `/start` shows an Allow / Deny bubble on the Mac, and only the first user can be paired that way. An allowed user can start turns in the chat that is open on the Mac, so treat their account like your own. A turn started from Telegram follows the same approval rules as one typed on the Mac. What the agent does without asking depends on its mode, so an allowed Telegram user can run whatever that mode lets through without a card, which is everything in `bypassPermissions`. Keep `telegram.allowedUsers` short. A request the agent does send goes to Telegram as Approve and Reject buttons as well as to the Mac, and Approve and Reject pick the agent's once-only option. Requests from background jobs and automation sessions go to the first allowed user the same way. Reads, searches and read-only tools run without a card. Files an allowed user sends are saved under `~/.ironpet/telegram/files/` (up to 20 MB each) and handed to the agent, and voice messages go to the transcription server from Settings → Voice. An allowed user can also approve or reject tool approvals of a turn they started, from Telegram. The token is in the Keychain item `ironpet.telegram`, never in `~/.ironpet`.
- **Inbox.** The chat agent and any program that can read `~/.ironpet/token` can list, read, add notes to, add, update, merge, mark done, resolve and remove Inbox items (`inbox_list`, `inbox_get`, `inbox_note`, `inbox_add`, `inbox_done`, `inbox_resolve`, `inbox_remove`) through the local server. `inbox_add` with an id still in the Inbox rewrites that item's title, notes, due date and link, and `same_as` adds a source to an item, so an agent can change what an item says. The item lists every source, so a merge stays visible. `inbox_resolve` takes an item off the list and keeps its title, sources, reason and time in `ironpet.db` for a year. The `IronPet inbox` command does the same through `POST /inbox` with the same token. Items and their notes are data in `ironpet.db` and never run anything, so these tools need no approval card, like memory-note edits. ironpet has no task list, no `tasks_*` tools and no `IronPet tasks` command. An automation with an `inbox` trigger runs once for each new item, and item text reaches it only through `{{item.*}}`, so the rules for poll items below apply to it: a shell action gets the text quoted, and a prompt that uses it runs in the background agent with no tools. An automation `prompt` action runs in your chat with the chat's full tools, so it can change Inbox items and files like anything you type there. An agent that creates or changes one needs your Approve first. A prompt that uses poll item data (`{{item.*}}`) never goes to the chat, because that text comes from outside. It runs in a background agent that gets no MCP tools and cannot change the Inbox, like the one for meeting summaries. Meeting action items come from what people said on a call, so they are only Inbox items you can mark done or remove, and they are never sent to an agent as instructions. The same goes for a watcher automation's `suggest_task` action: text from an email, a chat message or an issue only becomes an Inbox item, with control characters removed, length limits, at most 10 per run and only an http or https link. The agent is told that Inbox text is data.
- **System notices.** An automation with `report: "chat"` posts its answer to the open chat as a notice. The answer is the same text its bubble and thread already hold. ironpet sends it to the chat's agent once, inside an `<ironpet-meta>` block that says it is data and not instructions. Only ironpet code creates these blocks: any `<ironpet-meta` tag in text from you, a remote client or an automation answer is escaped before it reaches an agent. An agent can still be steered by what an answer says, as with any tool output. An automation with `session: "fork"` starts from a copy of the main chat's agent session, so its agent sees the conversation so far.
- **File previews on the phone.** A paired phone can read a file the chat's reply names, through `GET /v1/files/preview`. The Mac sends only files inside the folder the open chat works in, after `..` and symbolic links are resolved, so a link inside the folder cannot reach outside it. It never sends `.env*`, key or certificate files, `.netrc`, `.npmrc`, `.pypirc`, `credentials` files, or anything under `.ssh`, `.aws`, `.gnupg`, `.kube`, `.docker`, `.ironpet` or `keychains`, matched without regard to case. Only regular files are read. This list is not complete, so if you open a chat on your whole home folder, every other file under it can be previewed from a paired phone. Open chats on a project folder. A path outside the folder gets the same 403 whether or not the file exists. Text is cut at 256 KiB. This is read access to your project folder for any phone you paired, so revoke a phone you no longer trust in Settings. The path is in the query string, which the access log does not record.
- **Phone agent (off until you add a key).** The iPhone app can run its own agent that calls the Anthropic or OpenAI API straight from the phone, with a key you type into More → Phone agent. The key is in a Keychain item of the phone (service `dev.ironpet.remote.agent`, after first unlock, this device only, not synchronized) and in no file, `UserDefaults` or request to the Mac. What you type, and what its tools read for it (inbox items and memory pages from the Mac, calendar events, web pages it fetches), goes to that provider, so treat it like the chat agents' provider. Its tools are the inbox, read-only memory, the date, public web pages, the calendar and Reminders (each behind the iOS permission prompt). It has no tool that runs a command, edits a file or reaches another agent, and `web_fetch` refuses localhost, `.local` and private network addresses, also after a redirect. Text from pages, inbox items and memory is data, and the prompt says so, but a page that tries to steer the model can still skew what it adds to the inbox. The items it adds wait in `phone-agent-inbox.json` in the app's own storage, out of backups, until the Mac takes them with `POST /v1/suggestions`, which adds an item with a source of `agent` and a reference `iphone:<device id>`. A paired phone that registers its agent (`PUT /v1/devices/me/agent`) gets a row in the Mac's agent list and nothing else: no process, no pet, no chat, no permissions.
- **Background jobs.** A chat agent can start a job (`jobs_start`), which runs your chosen agent unattended in a folder ironpet already knows (the front Cursor window, the chat's folder, folders open in Cursor, folders of watched agent sessions, recent chat folders, or `~/.ironpet/scratch`); a path the agent makes up is refused. Starting, adding to and stopping a job asks first when the chat's mode asks about tools. A job runs in the agent's own mode. When the agent asks for permission, the job waits and ironpet raises an alert (alerts list, bubble beside the pet, macOS notification) that names the job, the tool and its input, with the agent's own options as buttons. The phone and Telegram show it with allow and deny. Only an answer from you approves, never a chat or spoken answer. After `jobs.permissionTimeoutMinutes` (10 by default) the agent gets its reject option and the job's result notes `permission timed out`. ironpet checks no command text: a job in `bypassPermissions` never asks, and it runs what the agent decides. Automation sessions (`new`, `own`, `fork`) follow the same rule, and their `allowedTools` and `disallowedTools` apply before any alert. The MCP connection a job gets (`/mcp/job`) does not offer the tools that start, steer, stop or open jobs, so the job's agent is not invited to start more. That is not a hard boundary: the job runs commands as you, and like the inbox tools, anything that can read `~/.ironpet/token` can reach the full `/mcp`. Its transcript is saved in `~/.ironpet/threads` and its prompt, folder and last step in `ironpet.db` for 30 days.
- **Assistant tools.** `status_*` tools let chat agents read the sessions ironpet watches (prompt snippets, summaries), open alerts, the Inbox, the brief and recap, and recent meeting summary lines with your open action items. They run without a card, like the inbox tools. What an agent reads through them goes to that agent's provider.
- **Memory.** Ghost's notes are claims on entity pages in `~/.ironpet/ironpet.db`, not files. Settings → Memory → Export writes Markdown copies to `~/.ironpet/memory-export/`, which nothing reads back. Earlier note files in `~/.ironpet/memory/` were read into the database once and are not read again; ironpet refuses an agent's edits in that folder. Through the memory tools, a claim an agent proposes is one line of at most 240 characters, and one that holds anything ironpet's secret patterns would redact (keys, tokens, passwords, card numbers) is dropped, not saved. The chat agent reads up to about 12 KB of claims at the start of each thread, and can save, forget and read them with the `memory_*` tools (see Approvals). Any chat agent can search, through `memory_search` and `memory_get` and without a card, your past chats with any agent (your messages and the replies, not tool output), meeting summaries and transcripts, the claims, and your screen captures when screen capture is on; what it reads goes to that agent's provider. An automation that runs in its own session has the same tools, but ironpet knows it is not your chat: its claims are marked with the automation, never go on your own page, need an explicit project, and it may not forget claims. A background job's session has the same memory tools as your chat, since it works on what you asked for: its claims are marked with the job (`job:<id>`) and go to the job's folder's project unless it names another, and it may forget claims. Its transcript is searchable like a chat's, but the reflection pass does not read it, because its first message is the chat agent's instructions, not yours. Claims and search results are facts recorded earlier and data, never instructions; the preamble and the tool descriptions say so, but a claim or a past message that tries to steer an agent can still skew what it does. A paired phone can read every page, fact and link through `GET /v1/memory` and `GET /v1/memory/pages/:ref`, and can pin or forget a fact or a page (`POST /v1/memory/facts/:ref/pin`, `DELETE /v1/memory/facts/:ref`, `DELETE /v1/memory/pages/:ref`); it cannot edit a fact or start the learning pass. A fact the phone forgets stays in the change log. The Memory section of the Mac window shows the same pages. Settings → Memory has Forget Everything, which deletes the claims, links, their index, the old note files in `memory/` and the Markdown copies in `memory-export/`.
- **Memory reflection (on by default).** Once an hour (`memory.digestMinutes`, 60 by default), ironpet sends what is new since the last digest: the new user and assistant messages of each chat (no tool output, at most 24,000 characters) with your notes that a new chat's preamble would hold, meeting summaries written since (`summary.md`, never the audio or the transcript) without your notes, and, only when `memory.learnFromScreen` is on (off by default), the text of new screen captures. Each goes to the agent that already had that text: a chat to its own agent, a summary to the summary agent that wrote it, and an automation's final answer to the agent that ran it (sent when it arrives, in your chat or its own session, without your notes). Screen text and merges go to the chat's agent, which can already reach captures through its tools; under an agent you picked in Settings → Memory (`memory.reflectAgent`), they go only when that is the chat's agent. Claude Code runs the pass on `haiku`; other agents on their default model. A page with more than `memory.maxClaimsPerEntity` (30) valid claims is merged: its oldest unpinned facts go to the digest agent, and pinned ones never do. With an agent picked, only text that went to that agent is read, and the rest is skipped. Either way no provider gets text it did not already have (the check is by agent). The text is sent to that agent again, though, and each pass spends its quota. That agent runs restricted, in `~/.ironpet/scratch/memory`, with no MCP servers and no memory or screenshot folders, and ironpet refuses every permission request from it, so it cannot change files or run commands. It answers with JSON: notes, the links it states between people, projects and tools, and merges. ironpet writes them. Meeting summaries, screen text and automation answers hold text other people wrote or what was on screen, so their notes may only describe people, never your page or a project, and may not replace existing claims; no pass replaces more than 5 notes in all. A name that fits more than one person is not guessed: ironpet asks you in the alerts, and nothing is sent for that. In `--test-mode` a pass runs only when an e2e scenario asks for one. Turn learning off under Settings → Memory → Learn from chats (`memory.reflect`); what was said while it was off is never sent later. Each pass is recorded as Memory in the Usage tab.
- **Automation auto-approve (off by default).** A `shell` action, shell poll source, `script` trigger or `prompt` that an agent on this Mac creates or changes waits for **Approve** in a bubble before it runs. ironpet window → Automations → **Auto-approve automation changes** (`automations.autoApprove`) skips that bubble for those Mac agents. It never covers an author whose id starts with `remote:` (a paired phone). Treat it like Auto mode for automations: a mistake still runs. Secrets do not belong in `automations.json`.
- **Stream automations.** A `stream` trigger keeps a shell command running as your user, with your login-shell `PATH`, for as long as the automation is on. An agent that creates or changes one needs your Approve before the command first starts, and again after every change to the command. Rejecting turns it off. ironpet starts the command in its own process group and stops the whole group when you pause, delete or change the automation or quit the app (SIGTERM, then SIGKILL after 2 seconds). Each output line is data from outside: it only fills `{{item.*}}`, which is quoted for the shell in a `shell` action, and a `prompt` that uses it runs in the restricted background session, as for polls. Lines over 64 KiB and more than 20 events a second are dropped, so a noisy command cannot flood the action. The command may not hold a literal token.
- **Morning brief and recap.** A `digest` action reads only what is already on the Mac (Inbox items, alerts, the activity log in `ironpet.db`, the sessions in memory and meeting summaries under `~/.ironpet/meetings`), runs no command and starts no agent, so it needs no approval, whoever created it. It writes only the run in the automation history and, for its schedule, the last slot it delivered in `automation_daily` in `ironpet.db`. The bubble and the Today page show Inbox item titles, alert titles and meeting action items beside Ghost, as the other bubbles do.
- **No API keys.** Chat goes through the sign-in your agent already has. If an agent says it needs you to sign in, ironpet shows a button: for an agent that signs in over ACP it calls `authenticate`, and for a terminal sign-in it opens Terminal with the command the agent gave. ironpet sends nothing anywhere itself, except the optional GitHub and Sentry polling below, voice notes, spoken replies and voice mode if you turn them on, and the Bun download above.

## The downloadable Mac build

The builds on the GitHub Releases page come from `.github/workflows/release.yml`, which runs on a GitHub runner from the tagged commit with the same `scripts/bundle.sh` as a local build. Each release starts as a draft, and each DMG has a `.sha256` file beside it. With Developer ID secrets in the `release` environment the app is signed with the hardened runtime and the DMG is notarized by Apple. Without them the file is named `-unsigned`, is signed ad hoc, and macOS blocks the first launch until you allow it. The hardened runtime needs two entitlements in `Resources/IronPet.entitlements`: `com.apple.security.device.audio-input` for voice notes and meeting audio, and `com.apple.security.automation.apple-events` for jumping to an iTerm tab and reading its working folder. The app is not sandboxed, so it reaches `~/.ironpet`, the agents' config files and the Accessibility API as it does from `install.sh`. The workflow runs only for a pushed `v*` tag that is on `main`, or by hand from `main`, never for a pull request, and it refuses a version whose tag points at a different commit. The signing and notary secrets are meant to live in a GitHub environment named `release` that admits only `main` and `v*` tags (CONTRIBUTING.md › Releasing the Mac app), because a repository secret would reach any workflow a collaborator pushes on any branch, whatever the workflow file checks. The environment is only a gate together with two settings the maintainer makes before adding the first secret: a tag ruleset that lets only admins create `v*` tags, and a required reviewer on the environment. Without them, anyone with write access could push a `v*` tag on a commit with an edited workflow and read the secrets. The build job has read-only access and builds with Xcode 16.4, so the app does not depend on Swift libraries that macOS 14 and 15 lack. It holds the signing certificate in a temporary keychain and the notary key in a temporary file, deletes both as soon as the app is built and packaged, and uploads the DMG as an artifact. It does not keep the repository token in the checkout. The repository's own build code, SwiftPM packages and the npm adapters installed with `--ignore-scripts` do run in that job while the secrets are present; the ruleset and the reviewer are what limit who can start it. When a certificate is present, a build that cannot be signed and notarized fails instead of falling back to an unsigned file. A second job, with no secrets, opens the uploaded DMG and runs the bundle checks on the app inside, which starts the bundled adapters (third-party code), so that code never runs next to the signing key. A third job is the only one that can write to the repository. It runs only after both earlier jobs pass, checks out nothing, runs none of the repository's code, and only turns that artifact into a draft release. It re-checks that the release is still a draft right before it writes, so a published release is never overwritten. The build is Apple Silicon only, because GitHub's macOS runners are arm64; the release notes state it. macOS may also ask for your login password once so the new build can read its Keychain items, and an old Accessibility entry for IronPet may need removing and adding again. macOS ties Accessibility, Screen Recording and Microphone permissions to the app's signature, so a release build asks for them again once if an `ironpet-dev` build was installed before.

## The Mac app updates itself

The Mac build checks `https://github.com/irtazahashmi/ironpet/releases/latest/download/appcast.xml` once a day and downloads a newer release in the background (Settings → General → Updates turns either off). The request carries only a User-Agent with the app and Sparkle versions, no identifier, and system profile sending stays off. Sparkle installs an update only when its EdDSA signature verifies against `SUPublicEDKey` in the running app, and the replacement must carry the same Developer ID as the app it replaces. A tampered archive, or one signed with another key, is rejected. The private key lives in the `release` environment as `SPARKLE_ED_PRIVATE_KEY`, next to the signing certificate, and is read by one workflow step; see CONTRIBUTING.md > Releasing the Mac app. An update never restarts the app while an agent turn, a voice note or a meeting recording is running, and one whose database schema is older than the data on the Mac is refused. A build from `scripts/install.sh` never checks for or installs updates.

## Uploading the iOS app to TestFlight

`.github/workflows/testflight.yml` archives IronPet Remote on a GitHub runner and uploads it to TestFlight, with the same `scripts/ios_testflight.sh` as a local upload. It runs only when someone starts it from `main` in the Actions tab, never for a pull request, tag or push, and it waits for approval from one of the required reviewers of the `testflight` environment (the maintainers who may ship a build; anyone with write access can start a run, and a reviewer can approve their own). It signs with an App Store Connect API key in that environment's secrets (`ASC_KEY_P8`, `ASC_KEY_ID`, `ASC_ISSUER_ID`), through Apple's cloud-managed signing, so no certificate or provisioning profile is stored anywhere. The environment admits only `main`; the secrets are not repository secrets, because a repository secret would reach any workflow a collaborator pushes on any branch. The key has the Admin role in App Store Connect, so it can do more than upload builds: it is kept apart from the Mac notarization key, and only the environment's secrets hold it. The job has a read-only repository token and no persisted checkout credentials. The key file is written with owner-only permissions, removed from the build's environment once decoded, and deleted in a final step even when the build fails. XcodeGen is a pinned, checksum-verified download. The job sends the build and its debug symbols to Apple and talks to Apple's developer services to create the signing certificate and profiles; nothing else leaves the runner. The repository's Swift packages are resolved in the job that holds the key: the direct dependencies are pinned to exact versions, but Xcode may resolve newer versions of their own dependencies on the runner, so third-party package code can run while the key exists. What limits this is who can start the job. `main` takes changes only through a pull request that passes the `build` check, but it needs no approving review, so the required reviewers on the environment are the real gate: before approving a run they open its commit and check `testflight.yml`, `scripts/ios_testflight.sh` and the iOS project for changes.

## Record links open inside the app

An `ironpet://<id>` link only opens a record in ironpet (a notification, a meeting and so on). It runs no command and sends nothing. ironpet registers the `ironpet` scheme in its Info.plist; the pairing link `ironpet://pair?…` is not handled on the Mac.

On the iPhone, a tapped record id asks the paired Mac for that record over the same authenticated connection (`GET /v1/records/:id`) and shows its fields in a sheet. The phone keeps nothing and sends nothing else; the Mac answers with what its own readers return for that kind.

## What ironpet reads

- `~/.config/gh/hosts.yml` and the `gh` CLI, only with GitHub alerts on (off by default).
- `~/.ironpet/sentry.json` and its Keychain token, only after you've configured Sentry.
- Cursor's `storage.json` and iTerm2 via AppleScript, to find the project you're working in.
- `~/.t3/userdata/environment-id`, only when you press Open on a session that ran in T3 Code, to build its `t3code://` link.
- The microphone, only while you record a voice note or dictate into another app with voice notes on (off by default). macOS asks for permission the first time you record, not before.
- The microphone and one app's audio (or all system audio, through ScreenCaptureKit), only while a meeting transcript is recording, with meeting transcripts on (off by default). macOS asks for microphone and Screen & System Audio Recording access the first time you start one.
- With the welcome back summary on (`welcomeBack.enabled`, on by default): the system idle time and screen-lock state every 2 s, wake-from-sleep notifications, and, once you have been idle past `reminders.idleResetMinutes` (or right after the Mac wakes), which apps are capturing microphone input (Core Audio's process list: bundle id and pid, no audio and no permission prompt). This decides whether you are away or on a call; nothing is stored or sent.
- Wispr Flow's local database, to pick up dictation while the chat is open.
- The general pasteboard, briefly, after you select text in a chat message and release the mouse. ironpet sends the same copy command as Cmd-C to read the selection for the "Ask about this" button, then puts your earlier pasteboard contents back. It never reads the pasteboard otherwise, and the selected text stays in the chat unless you send it.
- When you open the chat from another app and Accessibility is already trusted (for screen capture or desktop control), the focused element's `AXSelectedText` once, so a removable context chip can offer that selection with your next message. Secure text fields, ironpet itself, denylisted and user-excluded apps, and private browser windows are skipped. Nothing is read in the background, and ironpet never prompts for Accessibility for this alone. The selection reaches the agent only if you send the message (or you remove the chip first). Once sent, it is saved with that message in the thread in `~/.ironpet/threads/` and shown above the message, and a paired phone receives up to 2,000 characters of it with the chat.

## Screen capture reads other apps and stores their text

Screen capture is off by default. Turning it on in Settings asks macOS for Accessibility access. Screen Recording is asked for only when you also turn on the screenshot fallback.

- **What is read.** The text of the focused window through Accessibility: static text, headings, text areas and text fields, as a tree. Buttons, menus and similar controls are read for their name only. Hidden elements are skipped. Secure text fields are never read: the source reads their role and nothing else, so their value never enters ironpet's memory. Password managers and other denylisted apps, private browser windows, non-web URLs and the locked screen are skipped in Swift code that no setting can override. Private-window detection looks at window titles, so a window with an unusual title can slip through. Keyboard, scroll and click events are used as timing only, to decide when to capture. No key or pointer position is read.
- **Screenshot fallback.** Off by default. When a window has no readable text, ironpet takes a screenshot of exactly the window it read (matched by its window id, never another window of the app) with ScreenCaptureKit and reads it with Apple Vision. The image stays in memory and is never written to a file.
- **Redaction.** Before anything is stored, rules replace secrets in the text with `[redacted:<kind>]`: provider keys and tokens (AWS, GitHub, GitLab, Anthropic and other `sk-` keys, Stripe, Slack, Google, npm, SendGrid), JWTs, private key blocks, `user:password@` in URLs and secret URL parameters, `password=`, `token:` and `.env`-style assignments, card and bank numbers, and long random strings. These rules are patterns, so a secret in a form they do not know passes through them. The unredacted text is never stored. An optional on-device privacy filter can plug into the write and read paths (`CapturePrivacyFilter`). None ships yet.
- **Where it is stored.** In the `capture_window`, `capture`, `capture_fts`, `capture_node`, `capture_block_seen` and `capture_draft` tables of `~/.ironpet/ironpet.db`, with the file and its WAL files set to mode `0600`. The text is redacted and not encrypted. The database runs with `secure_delete` on, so freed pages are zeroed. A prune and Delete all captures also empty the write-ahead log with a checkpoint, which is best effort (it does nothing while a reader holds the log). The disk itself may keep older blocks, so "deleted" means removed from the database and its log, not wiped from the disk. Captures, block records, drafts and tree nodes no remaining capture uses are deleted after the retention setting (30 days by default). Captures stored by earlier versions are deleted on upgrade. Text you typed into a field is kept as a draft until it is sent or discarded, redacted like the rest.
- **Who can read it.** The agents you run in ironpet's chat, through the `screen_search` and `screen_window` MCP tools, over the same loopback server and token as the other tools. They return stored, redacted text. Whatever an agent reads goes to that agent's provider. ironpet itself sends nothing anywhere. The captured text includes what other people wrote, such as Slack messages, so tool descriptions tell agents to treat it as data, never as instructions. A message that tries to steer an agent can still skew what it does. The `screen_*` tools only read, so like the `inbox_*` tools they run without an approval card. An agent that also has shell or automation tools could act on injected text, so the worst case is not limited to a wrong Inbox item.

## Desktop control lets agents operate other apps

Desktop control is off by default (`desktopControl.enabled`, Settings → Screen). Turning it on asks macOS for Accessibility access if ironpet lacks it. The agents you run in ironpet then get the `desktop_*` MCP tools, over the same loopback server and token as the other tools.

- **What an agent can do.** Read any window's accessibility tree live (text, names and values, redacted like screen capture), press buttons, set or insert text, pick options, set checkboxes and expand rows, focus elements and raise windows, through Accessibility actions. Two tools go beyond that: `desktop_key` and `desktop_open_url`, described below. ironpet sends no mouse events. `desktop_screenshot` returns one window's picture when Screen Recording is allowed. The picture stays in memory.
- **What it cannot do, in Swift code no setting overrides.** Read or act on password fields (role only), password managers and the other denied apps, apps you excluded from screen capture, private browser windows, denied or non-web browser addresses, or ironpet's own windows. Nothing works while capture is paused or the screen is locked. Private-window detection looks at window titles, so a window with an unusual title can slip through.
- **Approval.** An action on an element or window whose text says send, pay, delete, submit or buy (generic verbs, not app names) waits for Approve in a bubble. A rejection or two minutes of silence fails it. The element is checked again after the answer. The check reads text, so a control with an icon and no name, or a label in another language, does not trigger it. Treat Auto mode accordingly, because Auto skips the chat's card for MCP tools.
- **Key events.** `desktop_key` posts a key down and key up to one app's process with `CGEvent.postToPid`. It never posts to the system-wide event stream, so a key reaches that app and no other. It goes to whatever element has the keyboard focus in that app, and the app is raised first when it is not in front. The same app, window and address rules as the other tools apply, and a key is refused while a password field has the focus. Cmd+Return, Cmd+Q and Cmd+W always wait for Approve. Return or any Cmd combo also waits when the focused window title or element text says send, pay, delete, submit or buy. Letters, Tab, Escape and the arrows never ask, so an agent can type text one letter at a time into a field that is not a password field, and into a control whose name carries no trigger word. The focus is read again after your answer, and a key that now needs approval but was not asked about is refused. The log keeps the key name (for example `key cmd+l`) and the focused element's role and name, which means keys typed one by one appear in it.
- **Opening addresses.** `desktop_open_url` opens an `http` or `https` address in a new tab of the browser the agent names, else the frontmost browser, else the default one. Other schemes (`file`, `javascript`, `data`, browser-internal pages, `mailto` and so on) and addresses with a user name or password are refused, and so are hosts on the screen capture deny list (the password manager sites). Opening a page can still send data: an agent can put anything it has read into the query string, and the page loads in your logged-in browser. It does not look at the browser window, so with a private window in front the page may open there. The log keeps the address with secret query parameters removed.
- **Prompt injection.** Everything on screen is written by other people and apps, and the tools tell agents to treat it as data. A page that steers an agent can still make it press something that has no trigger word. The approval gate and the log are the limits, not a guarantee.
- **What is kept.** Every action is stored in the activity log (`activity_events`, kind `desktop.action`) for 30 days: time, app name, window title (up to 80 characters), element role and name (up to 80), the action, its outcome and a short note. Values you or an agent typed are not kept. The log stays on this Mac. Whatever an agent reads goes to that agent's provider.

## Voice notes send audio to a server you choose

With voice notes on (Settings → Voice, off by default), each recording is uploaded as a WAV file to the base URL you set, along with the model name and, if you saved one, an `Authorization: Bearer` header carrying your API key. That may be a service such as OpenAI or Groq, or a server on your own Mac. ironpet does not choose the server or fall back to another. While the feature is off, the microphone is never opened and nothing is sent, apart from the one-second test tone that the Test connection button uploads when you press it. The key lives in the Keychain item `ironpet.voice` and is never written to `~/.ironpet`. Recordings are held in memory only: the last one is kept until its transcription succeeds, so Retry can send it again, and none is written to disk. A plain `http://` base URL sends audio and the key unencrypted, so use it only for `localhost`.

Dictation into other apps (`hotkeys.dictation`, default Control-Option-Space, active only with voice notes on) uses the same server and the same in-memory handling. When the recording starts, ironpet reads the focused field's frame through Accessibility to place the recording bar, and when the recording ends it reads the focused element again to decide where the text goes. Both reads happen only if Accessibility is already trusted, and ironpet never prompts for it. A secure text field gets no text: the transcript goes to the clipboard instead. Otherwise the text is set as the selected text of the field. If the app ignores that, ironpet puts the text on the clipboard, sends Cmd-V, and restores the earlier clipboard contents unless something else wrote to the clipboard meanwhile. The field's content is read only to check that the insertion changed it, and is not stored or sent.

When `hotkeys.dictation` is `fn`, ironpet asks macOS for Input Monitoring (only then, never at launch) and installs a listen-only `CGEventTap` for modifier-change and key-down events on the session. The tap sees every key-down system-wide, but ironpet reads only whether Fn is down and whether any key went down while it was. It stores and logs no key, never changes or blocks an event, and removes the tap when the shortcut changes or voice notes turn off.

**Spoken replies (off by default).** With Settings → Voice → Read replies aloud automatically on, the text of a chat reply is sent to the same base URL (`POST /audio/speech`, with the speech model, the voice and your API key) when the reply answers a message you sent from the chat (not from Telegram or an automation). With it off, reply text is sent only when you press a reply's speaker button or choose Read Aloud, and only for that reply. The button works with the switch off. A paired phone can ask for the same on its own voice socket (`tts.speak`): it names a message of the open chat, the Mac reads the text from its own chat and refuses a message that is not an assistant reply, so the phone cannot make the Mac send arbitrary text to the speech server. The socket uses the same device token as the other `/v1` routes. Only the reply's prose is sent: code blocks, tables, bare links and emoji are left out, and so is anything after the first minute or so. The audio that comes back is played and kept in memory only. With the feature on, Settings also asks the server for its voice list (`GET /audio/voices`) while the Voice page is open; with it off, opening the page sends nothing. Preview sends one fixed line, and only when you press it or turn the switch on. While spoken replies are on, ironpet checks every 2 s which apps are capturing microphone input (bundle id and pid, no audio and no permission prompt), so a reply is not read aloud over a call; nothing is stored or sent. With the feature off, no text is sent and nothing is checked. With a remote server, reply text leaves your Mac.

## Voice mode listens and acts on what you say

With voice mode on (Settings → Voice → Conversation, off by default), the voice-mode shortcut opens a conversation. Turning the switch on uploads the one-second test tone and speaks one fixed line, to check the server.

- **The microphone is open only during a conversation.** It opens when you press the shortcut and closes when the conversation ends: on goodbye, Esc, the shortcut, the set silence (20 s by default) or a call starting. Each utterance is cut out of the stream on this Mac (an energy level, no model) and uploaded as a WAV to the transcription server, like a voice note. Audio, yours and the pet's replies, is held in memory only and never written to disk. Only utterances are sent, each with about a second of the sound around it; the stretches in between are not.
- **What you say goes to the chat's agent.** The transcript is sent as a prompt to the chat's agent (and its model provider) in a session of its own, with your claims from the memory database (your page, and the people the message names) in its first turn. The reply's text goes to the speech server to be read aloud. The conversation is saved as a thread in `~/.ironpet/threads/`, and when it ends memory's reflection pass reads it like a chat you left (only when learning from chats is on).
- **The voice session can't run commands or edit your files.** Its permission requests are allowed only when they are a kind ironpet never asks about: reads, searches, fetching a URL, edits to ironpet's memory notes, read-only MCP tools, and ironpet's own tools (status, memory, projects, inbox, screen search, and starting, steering or stopping jobs). Everything else is refused with a note to use a background job. A background job started by voice runs under the same rules as any job: its permission requests wait for you in an alert, and nothing spoken answers it.
- **"Cancel that".** A job started from voice, or a finished job a voice follow-up restarts, is held until the pet has said what it started and 5 s more (at most 60 s in all), so "cancel that" stops it before its agent runs. A follow-up to a job that is already running reaches it after its current turn, as from the chat.
- **Wispr Flow mode.** With Listen with set to Wispr Flow, ironpet opens no microphone of its own. While the pill is up, ironpet is the active app and reads Wispr's local history (`~/Library/Application Support/Wispr Flow/flow.sqlite`, read-only) for entries addressed to ironpet, as the chat already does.
- **Calls and presence.** While voice mode is on, ironpet checks every 2 s which apps are capturing microphone input (bundle id and pid, as for spoken replies). A conversation doesn't start, and ends, during a call or a meeting recording. Spoken job updates are skipped then, and while the Mac has been idle for the away time under Reminders.
- **Esc is taken globally while a conversation runs**, so it ends the conversation from any app. It's released when the conversation ends.

## Meeting transcripts record other people

With meeting transcripts on (Settings → Meetings, off by default), starting a meeting records two tracks until you stop: your microphone ("Me") and the audio of the app you picked, or all system audio ("Them"). ironpet's own sound is excluded. Both are written as 16 kHz mono WAV chunks to `~/.ironpet/meetings/<date-time>/` and stay there after the meeting. They are your recording, so ironpet never deletes them; remove the folder when you no longer need it. At most one chunk (up to 5 minutes per track) is held in memory at a time.

- **Audio goes to the configured server.** Every chunk is uploaded to the base URL under Settings → Voice, with the model name and your API key if you saved one. A plain `http://` URL sends it unencrypted, so use it only for `localhost`. Chunks that fail are retried against the same server.
- **The transcript goes to the chosen agent.** When a meeting ends and "Summarize automatically" is on, the full text of `transcript.md` is sent to the agent set as the summary agent (an ACP agent such as Claude Code or Cursor), and from there to that agent's model provider. Turn the setting off and no agent runs. Summaries and transcripts are also in Ghost's memory index, so any chat agent can read them later with `memory_search` and `memory_get` (see Memory above), and the summary, not the transcript, can go to the memory reflection agent when it is also the summary agent.
- **The summary agent cannot change anything.** It runs over ACP in the meeting folder only (ironpet's memory and screenshot folders are not shared), and ironpet answers every `session/request_permission` from it with a refusal, so it cannot edit files or run commands. ironpet itself writes `summary.md` from the agent's text answer. The agent can still read files inside the meeting folder.
- **Regenerate sends the same data again.** Regenerating a meeting sends its saved audio to the transcription server and the new transcript to the summary agent, the same two destinations as the meeting itself, and only when you press the button. It writes `transcript.prev.md`, `summary.prev.md` and short-lived `*.new.md` files inside the meeting folder.
- **Consent.** Recording people without their consent is illegal in many places (for example §201 StGB in Germany). The first meeting shows a notice, the picker repeats it, and the recording status shows in the pet's bubble. You can close that bubble, but the pet then shows a red Recording button for as long as ironpet records, and clicking it brings the bubble back.
- **Permissions are asked late.** Microphone and Screen & System Audio Recording access are requested when you press Start recording for the first time, never at launch and never with the feature off.
- **Voiceprints (off by default).** With "Recognise speakers in meetings" on, ironpet computes a voice embedding for each speaker of the Them track on this Mac. Nothing is sent anywhere for this. After you name a voice, a 256 number centroid, the name, seconds of speech and a meeting count are kept in `~/Library/Application Support/IronPet/voices.enc`, encrypted with AES-GCM under a key in the Keychain item `ironpet.voiceprints`. It is biometric data about people who have not consented, so tell them. Settings has **Forget this voice** and **Forget all voices**, which delete the entries from the file at once. **Rename** re-seals the file with the same key and rewrites the old name in `transcript.md`, `summary.md` and their `.prev.md` copies under `~/.ironpet/meetings/`, each in one atomic write. The first time you turn it on, the models (about 21 MB) are downloaded from Hugging Face by FluidAudio.
- **The phone can read the text.** With the remote API on, a paired phone reads summaries and transcripts, rebuilds them, and stops a running recording. It cannot start one and never receives the audio. See "The remote API opens a listener" below.
- **Quitting.** Quitting ironpet during a meeting writes the audio captured so far and what is already transcribed. Chunks not yet transcribed are marked as such in `transcript.md`.

## The remote API opens a listener, off by default

Settings → Devices turns on a server that lets a paired phone read and change your Inbox, see the pet, its bubbles, your watched agent sessions and alerts and today's brief, press the pet's tricks and a bubble's buttons, chat with the agent, including answering its tool approvals, manage your automations, read your meeting summaries and transcripts, and change a few settings. It is off by default and nothing listens until you turn it on.

- **Where it listens.** Two listeners on port 47380 (`remote.port`). One is plain HTTP on 127.0.0.1, for a front such as `tailscale serve` that you run yourself. The other is HTTPS on the one network address you pick in Settings → Devices (Tailscale first, then Wi-Fi or Ethernet, or an address you type), so any device on that network can reach it, and on a public Wi-Fi so can strangers. Keep the remote API off there. ironpet never binds 0.0.0.0 and offers no all-interfaces option. The HTTPS side uses a self-signed certificate that ironpet makes once, served with the macOS TLS stack (Network.framework). While the listener runs, a copy of the key also sits in a keychain file in the temporary folder that ironpet creates with a random password, keeps unlocked while the listener runs (the password stays in memory only), and deletes when the listener stops. At start, ironpet also deletes `ironpet-remote-*.keychain-db` files that a crashed or killed run left in the temporary folder, except those of another running ironpet. Nothing goes into your login keychain. The QR code carries the SHA-256 of that certificate and the phone accepts only a server with that hash, so another machine on the same network cannot stand in for the Mac. The pairing endpoint (`POST /v1/pair`) is open to anyone who can reach the port, and only a valid single-use code gets past it. macOS may ask whether ironpet may accept incoming connections. A custom `https://` address means your own front, which has its own certificate and gets no pin. Never point a front at port 47321, the hook server, which has one shared token. The hook server stays on loopback.
- **Who can call it.** Every route except pairing needs `Authorization: Bearer <device token>`. Loopback gets no exemption. A device gets its token after you press Allow on a bubble that names it and the Mac. The token is 256 random bits and only its SHA-256 is stored. A device can do what the routes allow, except the `screen` scope below, which is off for every device until you turn it on in Settings → Devices. Revoke in Settings → Devices ends it at once, including its open sockets. Revoke all and rotate also replaces the Mac's certificate and restarts the HTTPS listener with the new one.
- **Pairing codes.** 128 random bits, single use, valid five minutes, stored as a hash. Five wrong codes close every open code. The page makes a code when it opens and closes it when it closes, and Regenerate code makes the old one stop working. The QR code carries the SHA-256 of the Mac's certificate. The key stays in `~/.ironpet/remote/identity.key` (mode 0600).
- **The iOS app keeps one Keychain item.** IronPet (the iPhone app, built from `iOS/`, on TestFlight as `dev.ironpet.app`) stores the Mac's address, the pinned certificate fingerprint if the link had one, and the device token as one Keychain item (`dev.ironpet.remote`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable), so a backup or iCloud Keychain never copies it. It talks only to the Mac address from the pairing link. A 401 or Unpair deletes the item.
- **The iOS app keeps the last chat it showed in one file.** `chat-<hash>.json` in the app's own Application Support folder holds the newest 50 messages of the Mac's chat, its title, agent and folder name, and the ETag the Mac gave for that page. Approvals, forms, the queue and a running turn are never saved. The file is excluded from backups and iCloud, uses file protection until first unlock, and is deleted on unpairing and on a 401. It is shown at launch, before the Mac answers, and is replaced each time the Mac sends a new page.
- **The iOS app keeps unsent messages in one file.** A message typed while the Mac is out of reach waits in `outbox-<hash>.json` in the app's own Application Support folder, with its text, time, reply reference and failure reason, and nothing else. A voice message or a message with photos also keeps its recording or photo bytes in files in a folder beside it (`outbox-<hash>.files`), with the same exclusion from backups and the same file protection. The recording is deleted once the Mac has turned it into text, and each photo once its message is sent. The file is not in the app group, is excluded from backups and iCloud, and uses file protection until first unlock. It holds at most 100 messages, a message older than 24 hours is not sent on its own, and the file and its folder are deleted when the outbox is empty, when the user deletes the last message, or when the app pairs again.
- **The iOS app keeps no Inbox on disk.** The Inbox tab reads `GET /v1/suggestions` each time it loads, and Done and Remove are online-only. An older phone build may still hold `tasksync-list-<hash>.json` and `tasksync-ops-<hash>.json` from before; the app deletes both at launch.
- **Limits.** 20 requests burst and 5 a second per token, 3 event sockets and 3 voice sockets per token, 5 pairing attempts a minute, and 10 unauthenticated requests a minute before a five-minute lockout. Bodies are capped at 1 MiB (20 MiB for `POST /v1/uploads` and `POST /v1/settings/background`) and headers at 64 KiB.
- **Voice.** A phone can stream microphone audio to the Mac on `/v1/voice` (16 kHz PCM, at most five minutes a stream). The Mac keeps it in memory, turns it into a WAV and transcribes it through the same voice server as a voice note, so the audio goes wherever that server setting sends voice notes. Nothing is written to disk. Spoken replies are off until the phone turns them on: the Mac then synthesizes the reply to a message that phone sent and sends the audio back over the same socket.
- **What is logged.** `remote_access_log` keeps, for 30 days, the time, device id, method, route template (`/v1/suggestions/:id/accept`), status, size and duration. It never keeps a token, pairing code, body, header, path or query, so no message text, file name or upload body reaches it. The server's own logger is silent. Pairing, refusal, revocation and lockouts also go to `activity_events` as `remote.*`, with the device name you saw in the bubble. A device's `X-Forwarded-For` value is shown in the device list as the client sent it and is never used for a decision.
- **Phase 2 routes read more.** A paired device sees agent session summaries, edited file names and the last reply the hooks reported (never a transcript), open alerts with their text and links, the brief and recap, and the bubbles on screen. It can acknowledge a session, dismiss alerts, press a trick and press a bubble's button, and it can send one chat message about a session or an alert (`POST .../ask`), which runs a turn of the chat's agent on the Mac like any other message. That is the same reach as a paired Telegram chat, with one difference: a message from the phone is sent when you tap Ask Ghost, with no prefilled step.
- **Bubbles with a decision stay on the Mac.** A bubble that asks for a decision that grants something (a chat tool Allow or Deny, an automation or desktop-control Approve or Reject, Telegram and phone pairing) reaches the phone without its buttons, and a press on one is refused with 404. The phone shows "Answer on the Mac". The chat is the exception since phase 3, below.
- **Phase 3: a paired phone drives the chat, including approvals.** A paired device can send messages into the chat that is open on the Mac, stop a turn, open a saved thread or start a new chat, and **answer every chat tool approval and agent question the Mac can**: `POST /v1/chat/approvals/:id` runs the same Allow or Deny as the button. There are no scopes, so whichever client answers first decides. A stolen, unlocked paired phone can therefore allow a shell command that the agent asked to run, and an agent that runs in Auto mode never asks. Revoke the device in Settings → Devices to end it. Phone messages are marked "iPhone" in the transcript and are never read aloud.
- **Chat settings from the phone.** `PATCH /v1/chat/options` lets a paired device change the open chat's agent, model, folder and **Auto** switch with the same code as the Mac's chat settings. It can turn Auto on, so the agent then runs non-destructive commands and file edits without a card (destructive commands still ask), which a paired device could already approve one card at a time. The Mac checks every field first. The folder must be one of the Mac's recent folders or "no project", so the phone cannot point the agent at an arbitrary path, and the agent must be one the Mac lists. Agent, model and folder answer 409 while a turn runs, as the Mac's menus are disabled then. The model is stored per agent and Auto for the open chat, as for a change made on the Mac. The chat snapshot now also lists the Mac's recent folder paths to the phone.
- **Background from the phone.** `POST /v1/settings/background` accepts one JPEG, PNG or HEIC image of up to 20 MiB as the raw body and makes it the custom chat background of the Mac and every paired phone. It needs the device token. The Mac checks the kind from the first bytes, not from the name or content type, and answers 415 for another kind. It stores the image in `~/.ironpet/backgrounds/` as `custom-<random>` (a HEIC is stored as PNG) and removes the previous custom image. For an image over 1.5 MB or 2400 px, the Mac also keeps a JPEG copy of at most 2400 px in `~/.ironpet/backgrounds/.phone/`, which is what `GET /v1/assets/<sha256>` serves to phones.
- **Uploads.** `POST /v1/uploads` accepts one photo or file of up to 20 MiB per request (every other route stays at 1 MiB) and stores it in `~/.ironpet/remote/files/<device id>/` as `<random>-<last path component of the name>`, so a name cannot choose a folder. The file stays on disk after the message: ironpet does not delete it. An upload id works for the device that made it, once, until the Mac app quits, and the file goes to the chat agent as an attachment. Telegram files in `telegram/files` work the same way.
- **Chat images.** `GET /v1/chat/messages/<id>/file` sends the image of an attachment message in the open chat to a paired device, found by message id and never by a path the phone names. It sends images only (by extension), up to 20 MiB, and the response is `no-store`. A request without a valid device token is refused with 401.
- **Assets are the one cacheable route.** `GET /v1/assets/<sha256>` serves pet sprite sheets and the custom chat background, found only by a hash that the manifest lists, with `Cache-Control: private, max-age=31536000, immutable`. It still needs the device token, and it sends no path or file name from the Mac's disk beyond the name of the sheet in the manifest. Every other route stays `no-store`. The phone keeps the files in its app container and deletes a hash the manifest has dropped after seven days.
- **Phase 4: automations, meetings and settings.** A paired device can list, pause, resume, run, delete, create and change automations, send "New automation…" to the chat, read and rebuild meeting summaries and transcripts, ask Ghost about a meeting, move a meeting to the Trash, stop a recording that is running, read a small part of `config.json`, change the keys listed below, pick a pet and read usage totals.
- **Automations from the phone never approve themselves.** The device is the author (`remote:<device id>`), so an automation it creates, or one whose command, script or prompt it changes, waits for Approve on the Mac. This holds when **Auto-approve automation changes** is on: that setting covers agents on this Mac and never a `remote:` author. Changing only the schedule or the text of a user's automation keeps it approved. No route approves or rejects, so the phone shows "Waiting for Approve on the Mac".
- **Meeting transcripts and summaries leave the Mac.** This changes the sentence above that meeting data goes only to the voice server and the summary agent. With the remote API on, a paired device reads the text of `summary.md` and `transcript.md` over the connection it paired on (TLS, or your own front). There are no scopes, so any paired device can read them. No route serves a `.wav` chunk or starts a recording, and the phone can stop one. The phone asks for Face ID or the passcode before it shows any meeting, asks again after five minutes in the background, keeps the text in memory only (the connection keeps no response cache on disk and the Mac sends `Cache-Control: no-store`), and marks the views private so the app switcher blurs them. Remote access reads of a transcript are in `remote_access_log` as the route template only. A phone that is unlocked and stolen with the app open, within those five minutes, can read meetings until you revoke the device in Settings → Devices.
- **Inbox scan.** With `tasks.inboxScan` on (off by default) ironpet sends the chat messages written since the last scan to the agent of that chat, and with `tasks.inboxScanScreen` on (off by default) the screen text captured since to the agent of the current chat. The agent runs with no MCP servers, in a scratch folder, with every permission request refused, and can only answer with JSON. Screen text comes from captures that already passed the skip list and the secure-field rule. A scan sends at most 12,000 characters per job and files at most 8 items. Items are text and wait for you to mark them done or remove them.
- **Settings the phone may change.** `pet.name`, a pet from the gallery, the reminder switches and minutes, `tasks.meetingSuggestions`, `welcomeBack.enabled`, `speech.enabled`, `speech.voice` and `chat.background`. `meetings.enabled` and `screenCapture.enabled` can be turned off from the phone and never on. A patch that names anything else, such as `voice.baseUrl` (which would send meeting audio and replies to another server), `remote.*`, `telegram.*`, `integrations.*`, `automations.autoApprove`, `hotkeys.*`, `editors` or `skills.*`, gets 403 and changes nothing. `GET /v1/settings` does not list those keys either. Keychain items are never read or written.
- **Phase 5: with the `screen` scope, redacted screen text travels to the phone.** This changes the statement above that screen capture text stays on the Mac and goes only to agents you run. A device gets the `/v1/screen/*` routes only after you turn on **Screen text** for it in Settings → Devices. The phone cannot ask for the scope, and without it every screen route answers 403. With it, the phone reads the capture status, the change list grouped by window, the outline or text of one capture, search hits with snippets, and can pause capture (not resume it). Each route calls the same `screen_window` and `screen_search` tools an agent uses, so the text is what an agent would see: secrets were redacted before it was stored, the read filter (excluded apps, private windows) applies on every read, and the tools' caps hold (30 change lines per window, 50 search results). Redaction is pattern based and misses what it does not recognise, such as a password written as a plain word, so assume anything you can see on the Mac can reach the phone. A device may make 200 screen requests an hour, and the 201st gets 429. `remote_access_log` has one row per request with the device, the route template and the time, never the query or the text, and Settings → Devices shows "Screen read N times today" per device. The phone asks for Face ID or the passcode when the Screen view opens and after five minutes in the background, keeps the text in memory only (no URL cache, `Cache-Control: no-store`), covers the view whenever the app is not active and marks it private. A stolen phone that is unlocked with the Screen view open, within those five minutes, can read screen text until you turn Screen text off or revoke the device.
- **What it does not do yet.** No push notifications. Voice over `/v1/voice` is covered above. Only the `screen` scope beyond the routes already listed, and only the inbox, pet, bubble, agent, alert, today, asset, chat, upload, automation, meeting, settings, usage, screen, voice and event routes. The Home Screen widget and Live Activity hold only the pet name, mood and badge (App Group `group.dev.ironpet.app`), never the pairing token or Mac address. The security posture, in particular a listener reachable from the local network or tailnet, full access for a paired device and a self-signed certificate, is not yet agreed with the maintainers.

## Integrations are off by default

| Integration | Default | Turn on |
| --- | --- | --- |

| Share MCP sign-ins across folders | Off | Right-click → Integrations (shows a warning first) |

| Meeting transcripts (microphone and app audio sent to that server, transcript sent to an agent) | Off | Settings → Meetings |
| Memory reflection (quiet chats' new messages sent again to the agent that already had them; on by default because nothing reaches a new provider) | **On** | Settings → Memory → Learn from chats |
